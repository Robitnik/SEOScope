# CLAUDE.md — The Yovth Clients Report

Внутрішній dashboard агенції для SEO/marketing-метрик (Ahrefs, Semrush, GSC, Reporting Ninja/GA4). Стек: FastAPI + один durable worker + SQLite (WAL) + vanilla-JS фронт. Інтеграції спираються на зовнішній пакет `AISeoTools` (`/home/elon/dev/seo/AISeoTools`), який підключається additive-namespace і **пінується на конкретний commit/tag**.

## Модель робочого процесу (для кожного агента)

### 1. Взяти таску
- Обери **один** файл із [doc/dev/new/](doc/dev/new/).
- Перевір поле **Depends on**: усі залежності мають уже лежати у [doc/dev/done/](doc/dev/done/). Якщо ні — візьми іншу таску.
- У межах однієї хвилі порядок довільний. Один агент → одна таска за раз.

### 2. Підготуватися
- Прочитай сам таск-план **повністю** + названі в ньому секції `PLAN.md`.
- Для фронту — обов'язково `frontend/AGENTS.md`.
- Звір спільні контракти у [doc/dev/new/task-02-shared-contracts.md](doc/dev/new/task-02-shared-contracts.md) (або у `doc/dev/done/`, якщо вже закрита).

### 3. Працювати строго в своїй зоні
- Редагуй **лише** шляхи зі списку **Owned paths** своєї таски. Мапа володіння — в `INDEX.md`.
- Файли інших тасок — **read-only**. Не «дороблюй мимохідь» чужий модуль.
- Спільні контракти (`app/integrations/contract.py`, `app/schemas/`) — read-only для всіх, крім `task-02`.
- Кодь **проти оголошених контрактів**, не чекаючи, поки інший агент допише реалізацію. Де потрібен ще неготовий модуль — став заглушку/фейк за контрактом і познач `TODO(task-NN)`.

### 4. Дотримуватись інваріантів проєкту
- `None`/відсутність даних ≠ `0`. Ніколи не підміняй відсутнє значення нулем.
- Колір/семантика зміни визначається `better_direction` метрики, а не знаком числа.
- Snapshot- і range-метрики не порівнюються однаково (див. PLAN §12).
- Секрети (API keys, паролі, session cookies) **не** потрапляють у БД, events, логи чи в помилки, віддані UI.
- Browser-профілі одного провайдера не запускаються паралельно (lock `(provider, profile_name)`).
- Зміни в `AISeoTools` — **тільки адитивні** (див. PLAN §8): не перейменовувати наявні функції/CLI, не міняти return shapes, нові аргументи — optional keyword-only з дефолтами. Перед злиттям — уся стара test suite зелена.

### 5. Перевірити якість
- Напиши тести свого рівня у `tests/unit/<module>/` (юніти модуля — відповідальність власника модуля).
- Прогони лінт, type-check і `pytest` свого модуля. Для фронту — візуальний loop і чекліст із `AGENTS.md §15–16`.
- Пройди **Definition of Done / Gate** своєї таски. Якщо gate не виконано — таска не готова.

## Коли таска готова — перенести new → done і задокументувати

Це і є вимога «після того як таска готова план переносимо у `doc/dev/done` і документуємо що і як».

1. Ще раз пройди всі пункти **Definition of Done** таски. Не закривай наполовину.
2. Перенеси файл плану (зберігаючи історію git):
   ```bash
   git mv doc/dev/new/task-NN-*.md doc/dev/done/
   ```
3. **У кінець** перенесеного файлу додай секцію за шаблоном нижче — це документація «що і як».
4. Онови статус таски в [doc/dev/new/INDEX.md](doc/dev/new/INDEX.md) (познач ✅ done), щоб інші агенти бачили розблоковані залежності.
5. Якщо змінив **публічний контракт** — синхронно онови `task-02` і попередь у Completion report (розділ «Contract changes»).
6. Закомить логічним коммітом. **Push/PR — лише коли користувач попросить.** Гілка ≠ `main` (працюй у feature-branch).

### Шаблон Completion report (додати в кінець плану)

```markdown
---

## ✅ Completion report

- **Дата:** YYYY-MM-DD
- **Гілка / комміт:** <branch> @ <sha>
- **Статус:** done | done-with-followups

### Що зроблено
Стисло, по суті: які можливості/модулі реально працюють.

### Як зроблено (ключові рішення)
- Архітектурні/технічні рішення і **чому** саме так.
- Головні файли: `шлях` — призначення.
- Відхилення від плану + причина.

### Контрактні зміни (Contract changes)
Що змінилось у спільних типах/API/схемі БД і хто це споживає. «Немає», якщо не було.

### Як перевірити (verification)
Точні команди: тести, `docker compose up`, curl/скрипти, кроки в UI.
Що саме має побачити перевіряльник.

### Тести
Які тести додано (unit/contract/integration/e2e) і що вони покривають.

### Follow-ups / борг
Свідомо відкладене, з посиланням на майбутню таску або як `TODO(task-NN)`.
```

## Правила паралельності (антиколізія)

- **Ніяких правок чужих owned paths.** Потрібна зміна спільного контракту → мінімальна PR у `task-02`, оголоси її в Completion report; інші агенти підхоплять із оновленого контракту.
- **Міграції БД** створює лише `task-03`. Інша таска, якій потрібне нове поле, описує його як запит у своєму плані/через `task-03`, а не редагує `migrations/` сама.
- **`pyproject.toml`/залежності** змінює лише `task-01`. Потрібна нова залежність — запит до `task-01` (можна тимчасово в completion report як follow-up).
- **Спільні тестові фікстури** живуть у `task-13`; свій модульний фікстур тримай локально у `tests/unit/<module>/`.
- Комміти — атомарні, в межах owned paths. Повідомлення коммітів — англійською, з `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`.

## Мова та стиль

- Документи, коментарі-пояснення і UI-копірайт — **українською**; ідентифікатори в коді — англійською.
- Посилання на код у відповідях — клікабельні markdown-лінки виду `[file.py:42](app/file.py#L42)`.
- Провайдер/метрика називаються **однаково** скрізь: catalog → API → фронт → фільтри → помилки.
