# task-22 — Sync modal: стадія перевірки сесій, статуси та кнопка «Увійти»

- **Пакет:** UX попапа збору — перевірка сесій із прогресом, per-service статуси, інлайн-логін, очікування й авто-продовження
- **Хвиля:** F (auth flow)
- **Depends on:** task-20 (тригер логіну), task-21 (стани, події, пауза/резюм)
- **ОБОВ'ЯЗКОВИЙ КОНТРАКТ:** [`../../../frontend/AGENTS.md`](../../../frontend/AGENTS.md)
- **PLAN.md:** §4.3 (sync modal і живий прогрес), §4.4 (стани), §9.2

## Мета

Реалізувати флоу, який оператор описав дослівно: **відкриваю попап → запускаю збір → бачимо перевірку сесій із прогресом → де сесія мертва, там статус і кнопка «Увійти» → тисну → запускається логін → після входу збір іде далі сам.**

## Обсяг

**Входить:**
- **Стадія «Перевірка сесій»** у попапі: список обраних сервісів, у кожного — статус у реальному часі (`перевіряємо…` → `сесія активна` / `потрібен вхід` / `не налаштовано`). Determinate-прогрес за реальною кількістю сервісів, без фейкових відсотків (`AGENTS.md §9`).
- **Кнопка «Увійти»** рівно біля тих сервісів, де сесія мертва. Натискання запускає логін (task-20) і переводить рядок у стан `Очікуємо входу…` з поясненням, **де саме** відкрилося вікно й що зробити.
- **Живе очікування:** щойно сесія стає активною — рядок сам змінює стан, а доріжка продовжує збір **без перезапуску job** (task-21). Оператор нічого не перезапускає руками.
- **Решта сервісів збирається паралельно** весь цей час — це видно в тому ж попапі (модель доріжок §9.1), щоб очікування логіну не виглядало як зависання всього.
- **Таймаут очікування** показується чесно: скільки лишилось і що буде далі.
- **Закриття попапа не скасовує job** (§4.3) — включно зі станом очікування логіну; повернення відновлює картину з історії подій.
- Статус `auth_required` **на картці клієнта** (task-21 його тепер віддає) з дією «Увійти», щоб не треба було відкривати збір заради діагнозу.

**НЕ входить:** механізм логіну (task-20), стани/пауза в job engine (task-21), сторінка клієнта (task-18).

## Стани, які треба покрити (`AGENTS.md §6`)

`перевіряємо` · `сесія активна` · `потрібен вхід` · `логін запущено / очікуємо` · `логін успішний, продовжуємо` · `таймаут очікування` · `не налаштовано` · `теплого Chrome немає` (запасний шлях task-20 із готовою командою) · `помилка запуску логіну`.

## Тести

- Мертва сесія → рядок сервісу показує «потрібен вхід» + доступну кнопку «Увійти».
- Поки триває очікування логіну — **інші сервіси видимо збирають далі**, попап не виглядає зависшим.
- Після успішного логіну стан оновлюється сам і збір продовжується без ручного перезапуску.
- Закриття й повторне відкриття попапа під час очікування відновлює стан із подій.
- Таймаут показує, що станеться далі; тупикових станів немає (`AGENTS.md §6`).
- Keyboard-only: «Увійти» досяжна, focus-visible, focus не губиться при зміні стану; `aria-live` для оновлень статусів.
- Українська копія (§14); статус не лише кольором (§7).

## Definition of Done / Gate

- [ ] Флоу «запуск → перевірка сесій → статуси → Увійти → авто-продовження» працює наскрізь.
- [ ] Кнопка «Увійти» є **лише** там, де сесія справді мертва.
- [ ] Очікування логіну не блокує й не приховує збір інших сервісів.
- [ ] Закриття попапа не скасовує job; повернення відновлює стан.
- [ ] Усі стани зі списку вище реалізовані; жодного тупика без наступної дії.
- [ ] Keyboard/`aria-live`/контраст пройдені; копія українська.
- [ ] Скриншоти до/після переглянуті; e2e `sync-auth-flow` зелений.

## Ризики

- Найлегше зіпсувати це «крутилкою без сенсу»: прогрес мусить відображати **реальну** кількість перевірених сервісів (§9), інакше повертаємось до фейкових відсотків.
- Стан очікування логіну живе довго — він мусить бути зрозумілим і після reload, інакше оператор перезапустить job і зіб'є доріжку.
