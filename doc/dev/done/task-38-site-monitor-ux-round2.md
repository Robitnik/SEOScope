## 1. Вічний скелетон — першопричина

### 1.1 Що видно

Секція `#mc-runs` («Check history») лишається `aria-busy="true"` з 42 скелетон-елементами й написом «Loading check history…» **назавжди**. Решта шести секцій сторінки доїжджають нормально. Заміряно в браузері (Playwright у контейнері `api`, клієнт LAXTON):

```
mc-actions  busy=false  skeleton=0
mc-robots   busy=false  skeleton=0
mc-sitemap  busy=false  skeleton=0
mc-pages    busy=false  skeleton=0
mc-runs     busy=true   skeleton=42   "Loading check history…"   ← зависло
mc-changes  busy=false  skeleton=0
mc-dns      busy=false  skeleton=0
```

У мережі при цьому **немає жодного запиту історії прогонів**. Єдиний `runs`-запит, що доїхав, — `runs?limit=1&kind=light`, і це поллер, а не історія. Жодної помилки в консолі, жодного 4xx.

### 1.2 Механізм

Три ланки, кожна окремо правильна:

**Ланка 1 — спільний ключ запиту.** [api.js:1225-1237](../../../frontend/js/api.js#L1225-L1237): `listMonitorRuns` передає в `request()` ключ **`monitor-runs-${clientId}`**, однаковий для всіх чотирьох викликів:

| Виклик | Навіщо | Файл |
|---|---|---|
| `{ kind: "full", limit: 1 }` | відновлення поллінгу після F5 | [monitor-client.js:576](../../../frontend/js/monitor-client.js#L576) |
| `{ kind: "light", limit: 1 }` | те саме, другою половиною `Promise.all` | [monitor-client.js:577](../../../frontend/js/monitor-client.js#L577) |
| `{ kind, limit: 1 }` | тік поллера під час прогону | [monitor-client.js:609](../../../frontend/js/monitor-client.js#L609) |
| `{ limit: RUNS_LIMIT }` | **сама таблиця «Check history»** | [monitor-client.js:1140](../../../frontend/js/monitor-client.js#L1140) |

**Ланка 2 — ключ означає «скасуй попередній».** [api.js:35-38](../../../frontend/js/api.js#L35-L38):

```js
async function request(path, options = {}, key = path) {
  controllers.get(key)?.abort();
```

Це вимога AGENTS.md §12 («abort obsolete fetches and prevent stale responses from overwriting a newer selection») і сама по собі коректна — але вона трактує **ключ як тотожність**, а тут під одним ключем живуть чотири різні наміри.

**Ланка 3 — скасування лишає секцію в скелетоні.** [monitor-client.js:1134-1147](../../../frontend/js/monitor-client.js#L1134-L1147):

```js
el.setAttribute("aria-busy", "true");
el.innerHTML = sectionSkeleton({ label: "check history", rows: 5, columns: 5 });
try { renderRuns(await listMonitorRuns(...)); }
catch (error) {
  if (isAbortError(error)) return;   // ← вихід без зняття скелетона
```

Порядок подій при завантаженні сторінки: `loadRuns()` ставить скелетон і стартує запит → `resumePollingIfActive()` майже одразу стартує **два** свої запити з тим самим ключем → перший із них убиває запит історії, другий убиває першого → історія падає з `AbortError` → `catch` бачить abort і виходить **не знявши `aria-busy` і не прибравши скелетон**. Скелетон лишається до кінця життя сторінки.

### 1.3 Два дефекти, не один

- **D1 (першопричина):** один ключ на чотири різні наміри. Побічний ефект того самого: рядки 576 і 577 **скасовують один одного** — `Promise.all` ніколи не отримує обидві відповіді, `.catch()` мовчки їх ковтає, тож **відновлення поллінгу після F5 не працює взагалі**. Симптом інший, причина та сама.
- **D2 (чому це назавжди):** гілка `isAbortError → return` не має жодного запобіжника. Навіть із правильними ключами будь-яке скасування (перемикання клієнта, швидкий повторний клік) лишає секцію в скелетоні назавжди — немає ні таймауту, ні фінального стану.

### 1.4 Це третій випадок того самого класу

У пам'яті проєкту вже записано (task-36): «`api.js` request-key має бути явним іменем **наміру виклику**, а не похідним від параметрів — спіймано двічі, вдруге на живому». Тепер утретє. Отже фікс має бути не точковий, а такий, що закриває клас:

- ключ формується з **наміру**, а не з ресурсу: `monitor-runs-history-${clientId}`, `monitor-runs-poll-${clientId}`, `monitor-runs-resume-full-${clientId}`, `monitor-runs-resume-light-${clientId}`;
- `listMonitorRuns` **перестає вигадувати ключ сам** — приймає його від виклику обов'язковим аргументом. Тоді забути про ключ стає неможливо: не передав — не скомпілювалось у голові автора, а не тихо зламалось на живому;
- те саме перевірити для решти `monitor-*` функцій `api.js` (`getMonitorChanges` викликається щонайменше тричі з різними `severity` — [monitor-client.js](../../../frontend/js/monitor-client.js) вантажить `state=open&severity=critical`, `state=open&severity=warning` і `state=open`; у мережевому лозі вони всі доїхали, але лише тому, що йдуть послідовно — це та сама міна).

### 1.5 Обов'язковий запобіжник (D2)

`loadRuns` (і кожен його близнюк: `loadPages`, `loadChanges`, `loadDns`) на гілці `isAbortError` **не має права лишати секцію busy**. Мінімальне правило: скасування знімає `aria-busy` і лишає попередній контент, або — якщо контенту ще не було — ставить чесний нейтральний стан із кнопкою «Retry». Скелетон живе лише поки справді щось летить.

## 2. «Перевірити» на кожній сторінці

Сьогодні перевірити одну сторінку неможливо: є тільки `Check now · Light` (головна + топ-GSC) і `Check now · Full` (усі 600+ URL, ~7 хв, 184 MB). Оператор, що виправив `noindex` на одній сторінці, змушений або чекати планового прогону, або ганяти повний.

**Рішення:** `POST /clients/{id}/monitor/pages/{page_id}/check` — синхронний, один HTTP-запит до сайту, віддає оновлений `MonitorPageDTO`.

- Реюз без нового коду збору: `_process_page` ([runner.py](../../../app/monitor/runner.py)) уже вміє рівно це — фетч, сигнали, відбитки, версія, зміни; політність і SSRF-гард уже в `fetch`.
- Патерн фронту вже є — per-row «Verify alt» (task-27) і per-target «Run» (task-29): кнопка в рядку, спінер на місці, оновлення одного рядка без перезавантаження таблиці.
- **Відкрите питання, яке треба вирішити свідомо:** `monitor_changes.run_id` — не-nullable FK на прогін, а `RunKind` сьогодні `light | full`. Три варіанти:
  1. **новий вид прогону `page`** (адитивно в `RunKind` + DTO) — журнал лишається чесним («що це було»), фільтр журналу за замовчуванням ховає `page`-прогони, щоб не засмічувати історію. **Рекомендовано.**
  2. дозволити `run_id = NULL` для змін поза прогоном — дешевше, але ламає інваріант «кожна зміна має прогін-джерело»;
  3. чіпляти до останнього прогону — найдешевше й **найгірше**: журнал почне брехати, а task-37 F4 щойно лагодив рівно цю брехню.
- Ре-чек **не має** обходити політність: той самий `HostThrottle`, і подвійний клік має віддавати `409`, а не другий запит (прецедент — `claim_target` у task-29).

### Що зроблено

У рядку таблиці Pages — кнопка «Check» зі спінером, оновлює лише свій рядок.

### Як зроблено (ключові рішення)

- **Ключі запитів — обов'язковий аргумент, не дефолт.** Розглядався варіант з опційним `requestKey` і фолбеком на старий похідний ключ (як уже було зроблено для `listClientMonitorChanges`/`listPortfolioMonitorChanges` в task-36/37) — відхилено для `listMonitorRuns` свідомо: це вже ТРЕТІЙ випадок цього класу помилки в проєкті, тож фікс мусить робити помилку неможливою на рівні виклику (`TypeError` без ключа), а не просто пропонувати правильний шлях.
- **`lang="en-GB"` виявився недостатнім для Changed since.** Живою перевіркою підтверджено: атрибут `lang` на `<input type="date">` НЕ перебиває локаль відображення порожнього плейсхолдера в реальному Chromium (плейсхолдер лишався `дд.мм.рррр`) — плейсхолдер керується мовою самого браузера, не сторінки. Залишив `lang="en-GB"` як best-effort і додав явний текстовий хінт `(YYYY-MM-DD)` біля лейбла — це вже не залежить від локалі браузера.
- **`is_baseline_run=False` безумовно для `run_single_page_check`.** Ця дія завжди націлена на сторінку, що вже існує в `monitor_pages` (вибрана з таблиці Pages) — тобто це за визначенням не перший погляд клієнта на неї, тож базового-прогону виключення тут не потрібне.
- **Per-page прогони сховані з «Check history», не позначені бейджем.** Обрано простіший з двох варіантів (фільтрація на клієнті замість нового API-параметра `kind=light,full`) — таблиця історії явно про клієнт-скоуп прогони; сама дія «Check» видима у своєму рядку, де вона і сталася.

### Контрактні зміни (Contract changes)

- **Новий ендпоінт:** `POST /clients/{client_id}/monitor/pages/{page_id}/check` → `MonitorPageDTO`, `404` (клієнт/сторінка), `409` (перевірка вже триває).
- **`RunKind`** (`app/schemas/monitor.py`) розширено адитивно: `Literal["light", "full"]` → `Literal["light", "full", "page"]`. Споживачі: фронт (`monitor-client.js` фільтрує `page` з Check history), будь-який код, що читає `MonitorRunDTO.kind`.
- `GET .../monitor/runs` і `POST .../monitor/runs` НЕ приймають `kind=page` (лишились `Literal["light", "full"]`) — свідомо: per-page чек стартує лише через свій власний ендпоінт, не через загальний "Check now".
- OpenAPI-знімок (`tests/unit/api/data/openapi_snapshot.json`) перегенеровано й зафіксовано в тестах.

### Тести

- `tests/unit/frontend/monitor-request-keys.test.mjs` (новий) — `listMonitorRuns` без ключа кидає; однаковий ключ скасовує попередній виклик; різні ключі не скасовують одне одного.
- `tests/unit/monitor/test_page_check.py` (новий, перейменовано з задокументованого в таску `test_runner.py` через конфлікт basename із `tests/unit/jobs/test_runner.py`) — версія + зміна пишуться так само, як у повному прогоні; інші сторінки не чіпаються; конкурентний виклик кидає `PageCheckConflict`, лок звільняється навіть на щасливому шляху.
- `tests/unit/api/test_monitor_api.py` — 4 нових тести: 404 (невідомий клієнт/сторінка), 200 з оновленим DTO, 409 на паралельний виклик.
- `tests/e2e/frontend/monitor-smoke.cjs` — розширено живий прохід: асерт «жодна секція не aria-busy через 10с» одразу після заходу на сторінку клієнта і повторно після `page.reload()`.

### Follow-ups / борг

- DoD-пункт «F5 під час `Check now · Full`» перевірено на `Light`, не `Full` — той самий код-шлях (`resumePollingIfActive` не розрізняє kind), але свідомо обрано менш навантажувальний варіант для живого клієнтського сайту. Якщо потрібна саме `Full`-версія — рекомендується прогнати вручну одноразово, не автоматизувати в smoke-тесті (повний прогін ~2-3 хв і 99 МБ трафіку на клієнта за раз).
- `tests/e2e/frontend/monitor-smoke.cjs` не натискає кнопку per-page «Check» (лишає файл read-only, як задокументовано в його власному коментарі) — покриття цього шляху лишається на рівні unit/API-тестів.
