## Мета

Оператор має отримувати звіт **не з термінала**. Три кліки, чесна оцінка часу **до** старту, видимий прогрес, і жодного «звідки взялося це число» — походження кожної клітинки лишається на відстані одного кліка.

Окремо: сторінка мусить чесно показувати те, що двигун тепер уміє знати — **збіг або розбіжність між PDF і API** (task-42 §3.6). Це головна нова інформація, якої в старому CLI-процесі не існувало.

## 2. Сторінка `#/reports` — історія

Верх: заголовок, кнопка **Generate report** (primary), фільтри — клієнт, тип, шлях (API/PDF), статус.

Таблиця прогонів, найновіші зверху:

| Client | Report | Periods | Source | Status | Cross-check | Duration | Files | Created |
|---|---|---|---|---|---|---|---|---|

- **Report** — тип + коротка сигнатура періодів (`Monthly · 6 periods`, `Comparator · Jul 2026 → 2023`).
- **Source** — чіп `API` / `PDF` (не колір-онлі: підпис у чіпі).
- **Status** — чіп `Queued` / `Running` / `Succeeded` / `Partial` / `Failed` / `Cancelled`, кожен з іконкою й текстом.
- **Cross-check** — тільки для PDF-прогонів: `Match` / `Within tolerance` / `Mismatch` / `—`. `Mismatch` — найпомітніший елемент рядка, це знахідка, а не шум.
- **Files** — кількість (`6 PDF · 1 XLSX`), клік веде в деталь.
- Живі рядки (`queued`/`running`) мають інлайн-прогрес `3 / 6` і оновлюються без перезавантаження сторінки.

Стани (AGENTS §6): порожньо (перший запуск — з поясненням і кнопкою Generate), скелетон за формою таблиці, помилка завантаження з retry, «нічого не знайдено» під фільтрами (окремо від «взагалі порожньо»).

## 3. Попап запуску — майстер із 3 кроків

`<dialog>`, фокус-пастка, `Esc` закриває, повернення фокуса на кнопку (AGENTS §7).

**Крок 1 — Type.** Чотири картки з однорядковим поясненням:
- `Monthly` — 6 standard periods (month, quarter, YOY)
- `Yearly` — year over year
- `Custom months` — pick up to 24 months
- `Comparator` — same month across up to 4 years

**Крок 2 — Parameters.** Клієнт (обов'язково; паузовані — з позначкою, але доступні), далі — залежно від типу:
- `Monthly` — нічого, лише прев'ю обчислених діапазонів («This Month: Jul 1 – Jul 31, 2026»). Оператор бачить, що саме поїде в кабінет, **до** старту;
- `Yearly` — вибір років (2–4) + перемикач `Year to date` / `Full year`, із поясненням, що YTD порівнює однакові проміжки;
- `Custom months` — сітка місяців із перемиканням року, лічильник `7 / 24`, кнопки `Last 12 months` / `Clear`;
- `Comparator` — вибір місяця, далі до 4 років; спроба змішати різні місяці блокується **в UI** з підказкою «Use Custom months for different months», а не 422-ю з бекенда.

Незмінна вимога: неповний (поточний) місяць вибрати можна, але колонка одразу маркується `Partial` — і в майстрі, і в таблиці результату.

**Крок 3 — Source.** Дві картки з чесною ціною:
- **API — fast.** `~12 s`. Підпис: `Same numbers as the PDF report, verified.`
- **PDF — evidence.** `~4–7 min`. Підпис: `Downloads the actual client-facing PDFs and cross-checks them against the API.`

Оцінка часу рахується з `GET /reports/types` × кількість колонок — не хардкодиться на фронті. Для PDF додатково видно, скільки колонок візьметься **з кешу** (тоді оцінка падає), і чекбокс `Force re-download`.

Кнопка `Start` вимкнена, доки конфігурація неповна, і поруч завжди видно причину.

Якщо у клієнта не збережена назва звіту в кабінеті, крок 3 для PDF показує блок дискаверингу: кнопка `Find report`, список кандидатів, вибір, збереження. Це єдине місце, де оператор взагалі про це дізнається — і воно з'являється саме тоді, коли потрібне.

## 4. Деталь прогону — живий режим

Заголовок: клієнт, тип, шлях, час старту, кнопка `Cancel` (для `queued`/`running`).

**Прогрес по колонках.** Один рядок на період: назва, діапазон дат, стан (`waiting` / `running` / `done` / `failed` / `cached`), тривалість. Це не абстрактний бар на 60 %, а список того, що реально відбувається — рівно як вимагає AGENTS §9 («прогрес мусить бути правдою»).

**Живі логи.** Панель із SSE-потоку `GET /runs/{id}/events`: час, рівень, повідомлення. Автоскрол з кнопкою-пауза, фільтр за рівнем, `Copy log`. Рівні розрізняються не лише кольором (іконка + підпис). Перепідключення й `Last-Event-ID` — на боці існуючої логіки `sse.js`; переклад станів «connecting / reconnecting / live» — видимий, як у модалці збору.

**Після завершення:**
- **Таблиця** — 8 рядків × N колонок + колонки змін. `None` рендериться як `—` і ніколи як `0`. Числа — табличні цифри, локаль-аware. Клік по клітинці відкриває походження: для PDF — місце в PDF + ім'я файлу (і кнопка «Open that PDF»), для API — які поля/розмірність питались.
- **Cross-check** — банер: `All 48 values match` / `2 values differ` з переліком. Для `mismatch` — таблиця «метрика · період · PDF · API · Δ».
- **Files** — XLSX (кнопка `Download`) і список PDF: `View` (iframe-переглядач у drawer, `?disposition=inline` — CSP `default-src 'self'` це дозволяє) і `Download`. Скріншоти збоїв — окремою секцією `Diagnostics`, згорнутою за замовчуванням.
- **Failed/partial** — що саме не вийшло, який період, повідомлення помилки як текст (ніколи `[object Object]` — урок task-37), кнопка `Retry` (створює новий прогін із тими самими параметрами, кеш підхоплює вже завантажене).

## 5. Обов'язкові технічні правила (уроки цього проєкту)

1. **Ключ запиту в `api.js` — це намір, а не ресурс.** `request()` скасовує попередній виклик з тим самим ключем. Історія прогонів, поллінг живого рядка й завантаження деталі — **три різні наміри**, отже три різні ключі (`reports-history`, `reports-run-poll-<id>`, `reports-run-detail-<id>`). Це вже двічі ламало Site Monitor (task-36/38) — тут воно не повториться.
2. **Жодного інлайн-`style=`** — CSP блокує. Усе через класи й токени.
3. **Нових кольорів не вигадуємо** — лише `tokens.css`; чіпи станів переиспользуються з наявного словника (`state-*`, `tone-*`), нових не плодимо.
4. **Скелетони за формою контенту**, не сірі прямокутники навмання (task-38).
5. **Копірайт — англійська**, включно зі статусами, тултипами й помилками (CLAUDE.md).
6. **`translate="no"`** на іменах клієнтів, назвах звітів у кабінеті та іменах файлів.
7. Модулі імпортуються з тим самим `?v=` cache-bust, що й решта фронту.

### Як зроблено (ключові рішення)

- **Прев'ю періодів — клієнтський порт `app/reports/periods.py`.** Бекенд не має dry-run
  ендпоінта (`POST /runs` — єдине місце, де рахуються періоди), тож `computeReportPeriods()` в
  `api.js` відтворює точно ту саму дато-арифметику (ref = останній повний місяць, ковзні квартали,
  YTD-вирівнювання) — один порт, використаний і в майстрі (крок 2), і в fixture-рушії для
  реалістичного прев'ю. Розбіжність з бекендом — риск, задокументований прямо в коді як єдине
  місце, де це може задрейфувати.
- **Живий прогрес по колонках — похідний із самого потоку подій, не з окремого поля.**
  `ReportRunDTO` не має по-періодного стану (лише `periods_done`/`periods_failed` — лічильники).
  `reports-run.js`'s `derivePeriodRows()` читає `stage`/`level`/`details.period` з подій рушія
  (`app/reports/runner.py`'s `emit(level, stage, message, {"period": label})` — той самий
  контракт, що й `ninja_browser.py`) і будує рядки `waiting → running → done/cached/failed`. Це
  чесно відображає те, що двигун реально знає в кожен момент, а не вигадує проміжний стан.
- **Крос-перевірка й "походження клітинки" — inline, не floating-попап.** Спершу зробив
  floating popover з `element.style.top/left`, обчисленими з `getBoundingClientRect` — і живий
  гейт негайно впіймав CSP-порушення (`default-src 'self'`, без `style-src 'unsafe-inline'`,
  той самий бар'єр, що `sync-modal.js` вже документує для progress-барів). Переписано на inline
  `<tr>` під клітинкою, що розкривається/згортається — нуль позиціювання, нуль CSP-ризику, і
  краще читається в щільній таблиці.
- **Клік по клітинці — справжня `<button>` у `<td>`, не `tabindex`-хак.** Перша версія клітинок
  була `<td tabindex="0">` з click-обробником — фокусується, але Enter/Space не синтезують клік на
  нативно-неінтерактивному елементі. Живий e2e-прогін (клавіатурний тест) це впіймав. Виправлено
  на `<button>` всередині `<td>` (AGENTS §7 — ніколи клікабельний div/span).
- **Головні файли:** `frontend/js/{reports-page,reports-wizard,reports-run}.js`,
  `frontend/css/reports.css`, `frontend/fixtures/reports-{types,runs,empty,run-bundle}.json`,
  `tests/e2e/frontend/reports.cjs`. Адитивні дотики: `frontend/index.html` (пункт нав, `<main>`,
  діалоги майстра й перегляду файлу), `frontend/js/router.js` (маршрути `#/reports`,
  `#/reports/<runId>`), `frontend/js/api.js` (увесь REST-шар + fixture-рушій із
  `computeReportPeriods`), `frontend/js/formatters.js` (мета-словники статусів/джерела/крос-чеку +
  форматери тривалості/розміру файлу).
- **Відхилення від плану:** «скільки колонок візьметься з кешу» (§3, крок 3) **не** показано
  точним числом — бекенд не має ендпоінта, що рахує це до старту прогону (`_split_cached`
  — внутрішня логіка `runner.py`, не REST-виклик), а рахувати periods + `find_cached_file` на
  фронті означало б дублювати ще один шматок бізнес-логіки без потреби. Замість вигаданого числа
  — чесний застережний напис під оцінкою PDF-шляху («Closed periods already downloaded before are
  reused from cache — actual time can be lower»). Задокументовано як Follow-up нижче.
