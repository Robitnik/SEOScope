### 1.3 Єдина справжня розбіжність EFFYS — семантична: PDF `0` проти API `None`

Усі 4 незбіжні клітинки в кожному прогоні EFFYS — одні й ті самі:

```
Users              Month YOY      pdf=0     api=None
Total Conversions  Month YOY      pdf=0     api=None
Users              Quarterly YOY  pdf=0     api=None
Total Conversions  Quarterly YOY  pdf=0     api=None
```

Property EFFYS не існувало в липні 2025, тож даних за YOY-періоди немає **в обох джерелах**. Але кодують вони це по-різному: GA4 через API не віддає рядків (→ `None`), а Reporting Ninja у PDF друкує в таблиці «Overall performance» літеральний `0`, і парсер чесно зберігає `0`.

**Найтонше:** той самий PDF кодує «немає даних» **двома способами одночасно** — у таблиці «Overall performance» це `0`, а в таблиці каналів рядків просто немає, тож `Organic Users`/`Direct Users`/`Organic Conversions`/`Direct Conversions` за той самий період парсяться в `None` і дають вердикт `match`. Тобто розбіжність не між джерелами, а між двома таблицями **всередині одного файлу**.

### 1.4 Дзеркальний бік тієї ж монети: фальшивий `match` на вигаданому нулі

У тих самих прогонах `Clicks`/`Impressions` за `Month YOY` дорівнювали `0` **з обох боків** — і вердикт був `match`. Але це збіг на числі, якого не існує: у GSC за той період немає даних, просто Reporting Ninja відповідала рядком нулів (діагноз і дискримінатор — task-45 §1.6).

task-45 уже полагодив **API-бік** (`date`-розмірність: нуль рядків → `None`). Перевірено на свіжих прогонах: `EFFYS Clicks Month YOY = —`, `3XE Clicks Month YOY = —`. **Наслідок, який треба усвідомити:** тепер PDF-бік лишився єдиним, хто каже `0`, тож наступний PDF-прогін EFFYS покаже **8 mismatch замість 4** — і жоден з них не буде справжньою розбіжністю даних. Без цієї таски крос-перевірка почне голосніше кричати саме тоді, коли даних стало *точніше*.

## 2. Що робимо

### 2.1 Дискаверинг через пошук, а не через зчит таблиці

`list_report_names` замінюється на пошуковий дискаверинг, який використовує той самий механізм, що вже працює для завантаження:

1. **Прицільно:** ввести `Client.name` у поле пошуку кабінету → отримати всі звіти цього клієнта (сервер фільтрує, віртуалізація не заважає).
2. **Повний список** (для блоку `others` і для `known_names`): пройти таблицю з прокруткою до стабілізації набору імен, з явним запобіжником на кількість ітерацій, і **позначити результат як повний або усічений**. Усічений список **не** використовується як підстава для `report_name_unknown` — недоведена відсутність не є доказом.

Перший крок робіт — відтворити замір §1.6 і зафіксувати в таск-документі, скільки звітів у кабінеті насправді та який із двох способів їх бачить.

### 2.2 Лікування наявних прив'язок + портфельний аудит

- **CLI `yovth-report audit-ninja-bindings [--fix]`**: для кожного клієнта з `ninja_report_name` перевіряє, що назва належить саме йому (префікс `Client.name`, звірка з кабінетом). `--fix` **знімає** хибну прив'язку (не вгадує правильну — вгадування і створило проблему) і пише подію.
- **Разова санація:** прив'язку SWM зняти. 11 клієнтів без прив'язки лишаються як є — вони чесно дають `422 report_name_missing`.
- **Видимість у UI:** якщо збережена назва не починається з імені клієнта, сторінка прогону й майстер показують попередження `Bound to another client's report` з кнопкою «переприв'язати». Хибна прив'язка не має бути невидимою, доки хтось не порівняє 48 клітинок.

### 2.3 Третій стан у крос-перевірці: `no_data`

Зараз вердиктів два, і обидва брешуть на порожньому періоді (§1.3, §1.4). Стає три:

| PDF | API | Вердикт |
|---|---|---|
| `None`/`0`-як-порожньо | `None` | **`no_data`** — не помилка, окремий підсумок «4 periods had no data in either source» |
| число | `None` | `missing_api` |
| `None` | число | `missing_pdf` |
| число | число | `match` / `within_tolerance` / `mismatch` як зараз |

Щоб ліва колонка була чесною, PDF-парсер має **розрізняти** «у таблиці надруковано 0» і «даних немає». Правило, виведене з §1.3: період, у якому таблиця каналів **порожня**, а «Overall performance» показує рівно `0` по всіх метриках, — це період **без даних**, і його `0` нормалізується в `None`. Справжній нуль (є рядки каналів, є ненульові сусідні метрики) лишається `0`. Правило застосовується **на рівні періоду**, не окремої клітинки — саме тому воно однозначне.

Підсумок прогону перестає бути «44 values differ» і стає розділеним: `X match · Y no data · Z differ` — щоб число в шапці означало те, що людина під ним розуміє.

### 2.4 Повторюваний аудит точності (те, що знімає потребу в ручному розслідуванні)

`GET /api/v1/reports/accuracy` + CLI `yovth-report accuracy-report`: пробігає останній успішний прогін кожного клієнта і зводить:

- прив'язки (правильна / чужа / відсутня);
- крос-перевірка: `match` / `no_data` / `differ` по клієнтах;
- клієнти без GSC (`Clicks`/`Impressions` = `—`, не `0`);
- періоди, у яких обидва джерела порожні (нормально) проти тих, де порожнє лише одне (треба дивитись).

Вивід — та сама таблиця, що в §1 цього документа, але побудована машиною за секунди.

### 2.5 Чого свідомо **не** робимо

- Не чіпаємо вибір полів API — він доведено правильний (§1.1, §1.2), і будь-яка «підстраховка» тут лише розмиє відповідальність.
- Не автовиправляємо прив'язки здогадом. Знімаємо хибну й просимо людину підтвердити правильну.
- Не ховаємо `mismatch` за толерантністю. Поріг лишається 0,5 % — розбіжність має лишатись помітною.

## 3. UI

### 3.1 Банер крос-перевірки

Замість `44 values differ` — три числа з різною вагою: `44 match · 4 no data · 0 differ`. `no data` подається нейтрально (це не проблема), `differ` — акцентом. Пояснення під банером називає найімовірнішу причину, коли **всі** клітинки розійшлись: «Every value differs — this usually means the client is bound to another client's Reporting Ninja report», з посиланням на переприв'язку.

### 3.2 Таблиця розбіжностей

Колонка `Δ` для `no_data` показує `—` і не фарбується червоним. Рядки групуються за вердиктом: спершу `differ`, далі `no data`. Сьогодні 48 рядків ідуть суцільним червоним списком, де 44 з них — шум.

### 3.3 Попередження про чужу прив'язку

У шапці прогону поруч із `Reporting Ninja report EFFYS-Internal report` — чіп `Foreign binding` (жовтий, з іконкою й текстом), якщо назва не починається з імені клієнта.

### 3.4 Порожній період у клієнтському документі (task-47)

Період без даних у жодному джерелі не малюється як `0` у тайлі й не опускає лінію графіка в нуль: тайл дає `—`, лінія — розрив. Цей пункт узгоджується з task-47 §3.2 і тут лише фіксується як спільна вимога.

## 5. Тести

- `pdf_parse` — на **справжніх** PDF-фікстурах: період EFFYS `Month YOY` (порожня таблиця каналів + нулі в Overall) → усі метрики `None`; період із реальними даними, де одна метрика справді `0` → лишається `0`;
- `verify` — матриця вердиктів (§2.3) на всіх дев'яти комбінаціях; підсумок рахує три числа окремо;
- `ninja_browser` — пошуковий дискаверинг знаходить назву, якої немає у першому екрані (регресія на §1.6); усічений список позначається як усічений;
- `api` — `known_names` з усіченого списку **не** дає `report_name_unknown`; попередження про чужу прив'язку у DTO;
- `cli` — `audit-ninja-bindings` знаходить SWM-подібний випадок; `--fix` знімає прив'язку й не вигадує нову;
- **живий гейт:** PDF-прогін EFFYS після змін дає `44 match · 4 no data · 0 differ`; PDF-прогін SWM після переприв'язки (або після зняття) не показує 44 розбіжностей.
