## §0. Чому це не «просто рефактор», а конкретний, підтверджений баг

### §0.1 Живий ланцюг: `get_or_create_asset` тримає writer-лок через мережевий фетч НОВОГО ассета

[app/webarchive/capture.py:330](../../../app/webarchive/capture.py#L330) (`_capture_assets_for_page`, цикл по черзі ассетів — той самий патерн повторюється в `backfill_css_assets` на [capture.py:963](../../../app/webarchive/capture.py#L963), окремий виклик CLI-команди `archive-backfill-assets`; фікс на рівні репозиторію закриває обидва місця одним рухом):

```python
asset = repo.get_or_create_asset(ref.url, key, kind=ref.kind)   # (1) флаш ТУТ, якщо ассет новий
...
else:
    version, result_kind = _check_or_fetch_asset(repo, asset, ...)   # (2) мережевий fetch() усередині
```

[app/db/repositories/web_archive.py:504](../../../app/db/repositories/web_archive.py#L504):

```python
def get_or_create_asset(self, url, url_key, *, kind):
    existing = self.get_asset_by_key(url_key)
    if existing is not None:
        return existing                      # відомий ассет — жодного флашу, це ОК
    asset = ArchiveAsset(url=url, url_key=url_key, kind=kind)
    self._session.add(asset)
    self._session.flush()                    # ← (1) новий ассет: SQLite бере writer-лок ТУТ
    return asset
```

[app/webarchive/capture.py:205](../../../app/webarchive/capture.py#L205) (`_check_or_fetch_asset`, перший рядок тіла):

```python
result = fetch(asset.url, throttle=throttle, stats=stats, ...)   # ← (2) мережа. Лок із (1) ще тримається.
```

Коміт (через `write_controller.submit`, [capture.py:383](../../../app/webarchive/capture.py#L383)) настає лише **після** `_check_or_fetch_asset` повернеться — тобто **після** мережі. Для сторінки, де вперше зустрічається N нових ассетів, це N окремих вікон «лок тримається на час одного мережевого round-trip», по одному на кожен новий ассет по черзі — саме там, де `archive_client_workers=6` паралельних клієнтів найімовірніше зіткнуться.

### §0.2 Решта 25 місць `flush()` — надмірні, не баг, але й не безкоштовні

Прочитано весь файл методом за методом ([повний перелік](../../../app/db/repositories/web_archive.py)). Патерн послідовний і без винятків:

- **Мутація ІСНУЮЧОГО рядка** (`claim_capture`, `update_capture_counters`, `request_cancel`, `finish_capture`, `touch_url`, `mark_url_gone`, `confirm_snapshot`, `confirm_asset_version`, `record_asset_check`, `mark_uploaded`, `mark_local_deleted`, `update_settings`) — усі просто `setattr(obj, ...)` на вже завантажений ORM-обʼєкт. `id` уже відомий, часові поля (`updated_at`, etc.) виставляються явним `utcnow()` у Python, не через `onupdate`-колонку. Викликач читає значення з ТОГО САМОГО Python-обʼєкта одразу після — це працює без жодного флашу, бо флаш стосується видимості в БД/для ІНШИХ сесій, а не значення атрибута в пам'яті. Флаш тут нічого не дає нікому, крім того, що трохи раніше бере лок, який і так буде взято при найближчому `session.commit()` контролера.
- **`record_replay_miss`** — повертає `None`, викликач ніколи нічого не читає з обʼєкта. Флаш тут не служить нічому.
- **`create_capture` / `get_or_create_settings` / `get_or_create_url` / `create_snapshot` / `create_asset_version` / `create_change` / `register_blob`** — потребують `.id` (або, для `register_blob`, `.sha256`, який і так переданий викликачем, не згенерований) одразу для повернення викликачу. Це єдина причина флашу тут: SQLAlchemy реалізує Python-side `default=` колонки лише під час flush.

### §0.3 Чому дублювання коміту (контролер однаково закомітить) не робить це нешкідливим

`write_controller.submit(session, fn)` → `commit_with_retry(session, fn)` → `fn()` (тут — сам `flush()`), потім `session.commit()`. Тобто зайвий `flush()` не додає ЗАЙВОГО коміту — але **бере лок РАНІШЕ**, ніж мав би. Для методів, після яких одразу йде ще робота на тій самій сесії БЕЗ мережі (більшість мутацій існуючого рядка) — це не має значення, лок і так тримався б до найближчого коміту. Але для `get_or_create_asset` (§0.1) — це різниця між «лок береться просто перед локальним закриттям транзакції» і «лок береться перед мережевим fetch()».

## §1. Фікс

### §1.1 Явний `id=new_uuid()` замість покладання на флаш

`from app.db.base import new_uuid` (репозиторії й так імпортують з `app.db.base` — `utcnow` уже імпортовано звідти в цьому ж файлі). Приклад для `get_or_create_asset`:

```python
def get_or_create_asset(self, url: str, url_key: str, *, kind: str) -> ArchiveAsset:
    existing = self.get_asset_by_key(url_key)
    if existing is not None:
        return existing
    asset = ArchiveAsset(id=new_uuid(), url=url, url_key=url_key, kind=kind)
    self._session.add(asset)
    return asset
```

`asset.id` доступний одразу — `new_uuid()` виконався в Python, до будь-якого доторку до сесії. Той самий патерн для: `create_capture`, `get_or_create_settings`, `get_or_create_url`, `create_snapshot`, `create_asset_version`, `create_change`. `register_blob` не потребує цього кроку — його PK (`sha256`) уже переданий викликачем.

Модель (`app/db/models.py`) **не змінюється**: `default=new_uuid` лишається як пасивний захист для будь-якого іншого коду, що колись створить рядок без явного `id` (тоді відбудеться звичайний флаш-час дефолт, як і зараз, — просто жоден з методів цього репозиторію більше на нього не покладається).

### §1.2 Видалити 25 залишкових `self._session.flush()`

Просто прибрати виклик — без заміни на щось інше. Метод, що зараз повертає мутований обʼєкт (`claim_capture`, `update_settings`, …), і далі повертає той самий обʼєкт з уже виставленими атрибутами; викликачу байдуже, чи флашнуто.

`WebArchiveRepository.flush()` ([web_archive.py:48](../../../app/db/repositories/web_archive.py#L48)) — публічний passthrough, лишається (перевірити виклики: якщо жоден зовнішній код на нього не покладається для чогось критичного, задокументувати як «залишено для сумісності», не видаляти без потреби).

### §1.3 Аудит викликів у `capture.py`/`cloud_sync.py`

Пройтись по кожному місцю, де репозиторний метод з цього списку викликається **напряму** (не через `write_controller.submit`), і переконатись, що жоден не покладався на побічний ефект «а раптом це заодно і закомітило». Очікування: жодного такого місця немає (усі прямі виклики — це читання або виклики всередині `commit_with_retry`-обгорнутого блоку, де фінальний `session.commit()` і так усе закомітить). Якщо аудит знайде виняток — задокументувати його в Completion report, а не тихо залишити зайвий флаш «про всяк випадок».

Прибравши флаш звідусіль «наосліп», перший прогін повного тестового набору дав **9 провалів з `FOREIGN KEY constraint failed`**: створити батьківський рядок і одразу, без коміту між ними, створити дочірній з FK на нього — рівно те, чого план не передбачив (§1.3 планувало аудит «чи покладається виклик на побічний ефект», але не розглядав саме крос-табличне впорядкування).
- **Виправлення — не відкат, а ТОЧКОВИЙ флаш у правильному місці**: замість повернення `get_or_create_asset`'s власного флашу (що знову відкрило б §0.1), `repo.flush()` (публічний метод, відновлено з чіткою документацією «тільки явний виклик, ніколи всередині мережевого I/O») додано у ДВОХ місцях у `capture.py`:
  1. `_check_or_fetch_asset` — **після** мережевого фетчу, **до** `create_asset_version` (яка посилається і на `asset.id`, і на щойно зареєстрований `blob.sha256` — обидва потенційно нові, обидва потребують флашу тут, не раніше).
  2. `capture_url` — одразу після `create_snapshot`, до `link_snapshot_asset`/`create_change` (обидва посилаються на `snapshot.id` щойно створеного рядка; жодного мережевого виклику між флашем і жодним з цих двох немає — коштує нуль часу утримання лока).
- **Паралельна сесія (task-65 follow-up) знайшла й закрила третій випадок незалежно, тим самим фіксом**: `_start_adhoc_url_capture` (`app/api/archive.py`) робить `get_or_create_url` + `create_capture` в одному виклику — той самий `repo.flush()` між ними, той самий коментар-обґрунтування. Обидві сесії зійшлися на ідентичному рішенні незалежно — гарний знак, що фікс правильний, а не випадковий.
- **Юніт-тест на flush-інваріант — свідомо не багатопотоковий** (§4.1 плану, урок хотфіксу `ca8d388`): SQLAlchemy-евент `after_flush` рахує реальні флаші за виклик; `test_no_eager_flush.py` перевіряє кожен метод ОКРЕМО (не одним ланцюжком — сусідній `create`, що робить власний existence-check SELECT, легітимно автофлашить попередній необкомічений рядок, це стандартна поведінка SQLAlchemy, не порушення інваріанта цього файлу). Другий тест перевіряє регресію прямо: у момент фейкового мережевого виклику рядок нового ассета ще НЕ видимий свіжому SELECT (через `session.no_autoflush`).

### Контрактні зміни (Contract changes)

Немає. Публічні сигнатури методів `WebArchiveRepository` не змінились (окрім видалення непублічного побічного ефекту); `flush()` лишився з тим самим ім'ям і сигнатурою, лише документація уточнена.

### Тести

- `tests/unit/webarchive/test_no_eager_flush.py` (новий, 4 тести) — жоден метод не флашить сам по собі (перевірено евентом, не мокнуто); `id` доступний одразу після `create_x`/`get_or_create_x`; мережевий фетч нового ассета доведено відбувається ДО того, як його рядок стає видимим (регресія на §0.1).
- Повний `pytest` (2390 тестів) — зелений, окрім тих самих 2 НЕ пов'язаних, наперед-існуючих провалів (`test_aiseotools_signatures`, дашборд-staleness у `test_tech_audit`) — жодного стосунку до archive/webarchive.
- Паралельна сесія доповнила `test_web_archive_repo.py`'s `_snapshot()`-хелпер і `test_archive_api.py`'s `_seed_snapshot()`-хелпери власним `repo.flush()` — той самий фікс, той самий клас проблеми, знайдений і закритий ними незалежно.

### Живий гейт (виміряно, не з фікстур)

Партія з 9 капчурів одразу (3XE 647 URL, ALPHA 1181, EFFYS 17, GOREPORT 251, GRP 32, HWELL 284, NYCHA 94, SHB 126, SWM 27) на щойно рестартованому воркері з фіксом:

- **Нуль** `archive_capture_crashed`, **нуль** `FOREIGN KEY constraint failed` за весь час спостереження.
- EFFYS і GRP завершились повністю: **17/17** і **32/32**, `urls_failed=0` в обох.
- Усі інші клієнти, що встигли прогнатись — **`urls_failed=0` по кожному** (3XE 108/647, GOREPORT 140/251, HWELL 60/284, NYCHA 60/94, SHB 52/126) — помітно краще за прогін одразу після `ca8d388` (той мав поодинокі ізольовані відмови окремих URL на кожному клієнті). Контенція справді зменшилась вимірювано, не лише «крашів більше нема».
- Один нотатний, **не пов'язаний** інцидент: `monitor_run_crashed` (логер `app.monitor.scheduler`, не archive) — крос-підсистемна контенція за той самий SQLite-файл під час важкого архівного batch'у; Monitor-підсистема сама впоралась (один клієнтський прогін впав, решта — ні), поза обсягом цієї таски (задокументовано в §2 плану як свідомо не наш борг).

### Follow-ups / борг

- **Той самий клас FK-впорядкування може існувати і в `app/db/repositories/monitor.py`** чи інших репозиторіях — не перевірялось (поза обсягом цієї таски), але патерн («flush одразу після add», «create+create без коміту між ними») варто мати на увазі, якщо колись торкатимуться того файлу так само.
- **Справжнє, повне усунення потреби у флаші взагалі** (ORM `relationship()` між усіма парами таблиць, щоб SQLAlchemy сортував INSERT'и автоматично) — свідомо не зроблено: два точкові `repo.flush()` дешевші й безпечніші за впровадження `relationship()` (каскади, лінива підвантаженість) у файлі, яким активно паралельно користувалась інша сесія просто зараз.
