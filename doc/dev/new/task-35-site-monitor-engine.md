## Мета (робота оператора, яку закриваємо)

Сьогодні агенція дізнається про катастрофу на сайті клієнта **від клієнта** або через тижні — з падіння трафіку в GSC. Розробник клієнта викотив реліз із `noindex`, хтось закрив сайт у robots.txt, зникла TXT-верифікація Google Search Console, підмінили DNS, прибрали GA4-тег — усе це невидиме доти, доки не почне падати те, що ми міряємо раз на тиждень.

Закриваємо: **сайт кожного клієнта перевіряється щогодини, повністю — що 3 години; будь-яка зміна robots.txt, sitemap, мета-тегів, індексованості й DNS фіксується з часом, зберігається назавжди і породжує сигнал відповідної серйозності; `noindex` і втрата верифікації Google — червоний, найвищий.**

### 1.2 Наївний алерт «у robots.txt зʼявився `Disallow: /`» дав би **хибну критику вже сьогодні**

У `exxxoticaexpo.com` рядок `Disallow: /` присутній — але у групах `meta-externalagent` та сусідній AI-бот-групі, тоді як `User-agent: *` має звичайний WordPress-набір правил. Текстовий діф або регекс по файлу закричав би «сайт закритий».

Крім того, той самий файл містить **інлайнові коментарі** прямо в директивах:

```
Disallow: /wp- # all files WP: /wp-json/, /wp-includes, /wp-content/plugins
User-agent: * # general rules for robots of all search engines
```

**Висновок:** robots.txt парситься у структуру «група user-agent → правила», коментарі відрізаються, діф — **семантичний, по групах**. Серйозність рахується тільки для груп, що стосуються нас: `*`, `Googlebot`, `Googlebot-Image`, `Bingbot`. `Disallow: /` для `GPTBot`/`meta-externalagent` — це `info`, не інцидент.

### 1.3 Сирий хеш HTML майже стабільний — але «майже» треба закрити

Два послідовні запити тієї самої сторінки з інтервалом 2 с:

| Сайт | Байти | `sha256` сирого тіла | Хеш сигналів | Хеш видимого тексту |
|---|---|---|---|---|
| laxton.se | 491 965 | стабільний | стабільний | стабільний |
| pjclarkes.com | 457 132 | стабільний | стабільний | стабільний |
| effyscafe.com | 167 818 | стабільний | стабільний | стабільний |
| nysapphire.com | 746 481 | стабільний | стабільний | стабільний |
| exxxoticaexpo.com | 437 605 | стабільний | стабільний | стабільний |
| **goreport.com** | 194 590 | **змінюється щозапиту** | стабільний | стабільний |

Причина єдиного розходження — Cloudflare-скрипт із per-request ідентифікатором: `window.__CF$cv$params={r:'a296eb4b7f40ca38',…}` → `{r:'a296eb58c97377a4',…}`. Дві зміни на 194 KB.

**Висновок — триярусний відбиток (ключове рішення таски):**

1. `signals_sha256` — канонізований JSON SEO-сигналів (статус, фінальний URL, meta robots, X-Robots-Tag, canonical, title, description, h1, hreflang, типи JSON-LD, знайдені GA4/GTM/GSC-ідентифікатори). **Саме він вирішує «змінилося?» і породжує алерти.**
2. `text_sha256` — нормалізований видимий текст (без `script`/`style`/коментарів, пробіли схлопнуті) → сигнал «контент переписали».
3. `raw_sha256` — сирі байти після маскування відомого шуму (CF-ray, `nonce=`, CSRF-токени). Це **доказ**, а не привід для алерту: сам по собі ніколи не підіймає серйозність вище `info`.

### 1.4 Обсяг і час: виміряно, а не на око

- Sitemap-и клієнтів: **16 … 608 URL**, сумарно **≈ 2 850 URL** на 14 клієнтів. Найбільший — `exxxoticaexpo.com` (608).
- Медіана сторінки — **442 KB**, медіана відповіді — **0,51 с** (p95 = 0,56 с), заміряно на 15 сторінках `nysapphire.com` послідовно з паузою 250 мс: 15 URL за **11,5 с** ≈ 0,77 с/URL разом із чемною паузою.
- Отже **повний прогін**: найбільший клієнт ≈ 7,8 хв; усі 14 послідовно ≈ 37 хв; при 4 клієнтах паралельно — **≈ 10–12 хв**. Це вкладається у 3-годинний цикл із запасом ×15.
- **Трафік**: ≈ 1,2 GB на повний прогін, ≈ **10 GB/добу** при 8 повних прогонах. Це реальна ціна вимоги «повна перевірка що 3 години», і вона керується налаштуваннями (§3.7), а не мовчки урізається.
- **Диск**: baseline зберігає повний код усіх 2 850 сторінок — **≈250 MB** gzip одноразово. Далі сторінки з незміненими сигналами **не** створюють ні рядка, ні блоба: приріст іде зі швидкістю реальних змін, а не прогонів (§3.2.1).

### 1.6 Залежностей додавати не треба, але `dnspython` у образі **немає**

Перевірено в контейнері: `httpx` ✅, `lxml` ✅, `pandas` ✅ (усі — транзитивно через optional-групу `local`, тобто **відсутні на CI/деплої без bind-mount**), `dns` ❌, `bs4` ❌.

Це та сама розвилка, яку вже проходили task-27 і task-29, і рішення повторюємо: **тільки stdlib** (`urllib.request`, `html.parser`, `ssl`, `gzip`, `difflib`, `xml.etree`). DNS — **DoH-запитами до `dns.google` і `cloudflare-dns.com`** звичайним `urllib` (перевірено: TXT/A/NS для всіх 14 доменів повертаються коректно). Побічна вигода: два незалежні резолвери показують реальну картину «як бачить світ», а не резолв усередині одного контейнера, і ловлять розбіжність під час пропагації.

Пам'ятка з попереднього досвіду проєкту: `poetry lock` у цьому середовищі не проходить (див. пам'ять `env_poetry_lock_limitation`), тож «нуль нових залежностей» — не естетика, а умова того, що таска взагалі збереться.

## 2. Обсяг (scope)

**Входить:**

1. Двигун перевірки: robots.txt, sitemap (index + вкладені + `.gz`), **усі** сторінки з sitemap, точки входу (http/https × apex/www), DNS через DoH, термін дії TLS.
2. Модель зберігання «стан + версії»: кожна зміна — нова незмінна версія з часом; **повний код сторінки** зберігається на baseline і на кожну зміну; однакові байти зберігаються один раз (content-addressed).
3. Двигун порівняння й таблиця серйозності: `critical` / `warning` / `info`, із самозагасанням сигналу, коли причина зникла; окреме правило для URL у sitemap зі статусом ≠ `200`.
4. Планувальник у worker-процесі: light щогодини, full що 3 години, джитер, дедуплікація, повага до паузи клієнта.
5. REST API: зведення, журнал прогонів, стрічка змін (клієнтська й портфельна), таблиця сторінок, історія версій, дифи, ручний запуск, ack, налаштування, експорт CSV/XLSX.
6. CLI: разовий прогін, статус, прибирання старих блобів.
7. Тести всіх рівнів + локальний фейковий сайт для наскрізного сценарію.

**Не входить (свідомо):**

- **Будь-який UI** — уся візуальна частина в [task-36](task-36-site-monitor-ui.md). Ця таска закінчується на API + CLI.
- **Канали доставки алертів** (Telegram/email/webhook). Підтверджено користувачем 2026-08-11: v1 — тільки UI. Модель даних до цього готова (`monitor_changes` із `severity`/`acknowledged_at`), доставка — окрема майбутня таска.
- **Рендер JavaScript.** Дивимось те, що віддає сервер, як Googlebot на першій хвилі; Chromium у контейнері немає (та сама межа, що в task-25).
- **Моніторинг чужих доменів** (конкуренти, проспекти). Об'єкт — домен клієнта з `clients.domain`.
- **Uptime-моніторинг із хвилинним інтервалом.** Найменший крок — година; це монітор змін, а не pager.
- **Автоматичне відкочування/виправлення.** Монітор лише спостерігає й доповідає.

## 3. Рішення

### 3.1 Це **не** провайдер і **не** `SyncJob` — окремий рушій

Спокуса переюзати джоб-двигун велика (task-25/26 саме так і зробили), але тут вона хибна, і ось чому:

| Аргумент | Наслідок |
|---|---|
| Частота: 24 light + 8 full на клієнта на добу × 14 клієнтів = **~450 прогонів/добу** | У `sync_jobs` зараз 703 рядки **за всю історію проєкту**. Монітор перекрив би її за півтори доби, і `GET /sync-jobs` перестав би бути операторською історією збору. `job_events` (9 927 рядків) роздувся б так само — при `event_retention_days = 30` це постійні сотні тисяч рядків у таблиці, яку читає SSE-стрім. |
| Клітинка джоб-двигуна — `(клієнт, провайдер, період) → snapshot → метрики/quality` | У монітора немає ні періоду, ні метрик: у нього безперервний ряд версій стану. Втискування дало б фіктивний `anchor_date` на кожен прогін. |
| Джоб-двигун тримає browser-профілі, auth-gate, семафор слотів, lease/recovery | Монітору не потрібне **нічого** з цього: звичайний HTTP до сайту самого клієнта, без логінів і метрованих юнітів. |
| Ціна перерваного прогону | Для Ahrefs — втрачені юніти й час; для монітора — нуль: наступний тік просто перевірить те саме. Durable-семантика тут не окупається. |

**Рішення:** `app/monitor/**` — власний легкий рушій у тому ж worker-процесі. Джоб-двигун (`app/jobs/**`, зона task-05) **не чіпаємо**, крім однієї проводки старту планувальника (§3.6). Взамін монітор наслідує *форму* доріжок: між клієнтами — паралельно, всередині клієнта — послідовно й чемно (PLAN §9.1).

### 3.2 Модель даних: «поточний стан + ланцюг незмінних версій»

Вимога «зберігати всі версії» в лоб (рядок на кожен URL на кожен прогін) дала б 2 850 × 8 = **22 800 рядків/добу**, ~8,3 млн/рік, з яких 99 % — «те саме, що вчора». Тому:

- **стан** — один мутабельний рядок на об'єкт (`monitor_pages`, `monitor_resources`, `monitor_dns_records`): оновлюється щопрогону, несе `last_checked_at` (це і є «дата й час збору» для незмінних об'єктів);
- **версія** — незмінний рядок, що дописується **тільки коли відбиток змінився**: несе повний набір значень, час спостереження, посилання на попередню версію й перелік змінених полів.

Так «усі версії» зберігаються буквально й повністю, а обсяг росте зі швидкістю **змін**, а не прогонів. Ланцюг `prev_version_id` дозволяє пройти історію будь-якого URL від першого дня.

Таблиці (`app/db/models.py`, успадкована зона; одна міграція `<rev>_site_monitor.py`):

| Таблиця | Роль | Змінність |
|---|---|---|
| `monitor_settings` | конфіг на клієнта: `enabled`, `base_url` override, інтервали, `max_urls`, `monitor_when_paused`, ігнор-патерни, приглушені типи змін | мутабельна |
| `monitor_runs` | **журнал прогонів** — kind (`light`/`full`), тригер, статус, час старту/фінішу, лічильники (перевірено URL / змінено / нових / зниклих, запитів, байтів), лічильники змін за серйозністю, `truncated`, помилка | мутабельна (дописується під час прогону) |
| `monitor_blobs` | content-addressed сховище: `sha256` (PK), розміри, mime, шлях до gzip-файла, `first_seen_at`/`last_seen_at` | append + оновлення `last_seen_at` |
| `monitor_resources` | поточний стан robots.txt і кожного sitemap-файла: URL, статус, `content_sha256`, розібрана структура, `version_seq`, `missing_since` | мутабельна |
| `monitor_resource_versions` | версія robots/sitemap: сира структура + `content_sha256` + `diff_summary_json` | **незмінна** |
| `monitor_pages` | стан URL: статус, фінальний URL, кількість хопів, `indexable`, директиви robots, X-Robots-Tag, canonical, title, description, h1, слова, знайдені analytics-ID, три відбитки, `in_sitemap`, `gone_since`, `is_key_page`, `consecutive_failures` | мутабельна |
| `monitor_page_versions` | версія сторінки: повний `signals_json`, три відбитки, посилання на блоб тіла, `changed_fields_json`, `prev_version_id` | **незмінна** |
| `monitor_dns_records` | стан `(client, name, type)`: відсортовані значення, TTL, резолвер, часи | мутабельна |
| `monitor_dns_versions` | версія DNS-запису | **незмінна** |
| `monitor_changes` | **стрічка змін/алертів**: серйозність, стабільний `change_type`, обсяг (`site`/`page`/`dns`/`robots`/`sitemap`), суб'єкт, старе/нове значення, посилання на версію, `acknowledged_at`, `resolved_at` | мутабельна (лише ack/resolve) |

Незмінність версій тримається тим самим `event.listen(..., "before_update", _reject_update)`, що вже стоїть на `ProviderSnapshot`/`MetricValue`/`GscDimensionMetric` ([models.py:669](../../../app/db/models.py#L669)) — інваріант проєкту, а не нова вигадка.

`monitor_blobs` — окрема таблиця, а **не** наявна `artifacts`: та жорстко прив'язана до `job_id` + `provider` ([models.py:306](../../../app/db/models.py#L306)), а тут немає ні джоби, ні провайдера. Файли лежать під artifacts root у `monitor/<sha256[:2]>/<sha256>.gz`; читання йде через ту саму перевірку «розв'язаний шлях усередині кореня», що й у task-25.

### 3.2.1 Зберігаємо повний код сторінок (підтверджено 2026-08-11)

Вимога — «зберігати весь код, щоб бачити зміни». Виконується буквально:

- **baseline**: під час першого прогону зберігається повне тіло **кожної** сторінки (2 850 сторінок × ~90 KB gzip ≈ **250 MB** одноразово — виміряно на медіані 442 KB);
- далі — **нова копія тіла тільки тоді, коли змінився `signals_sha256` або `text_sha256`**. Це не «економія на історії», а захист від неї: `goreport.com` міняє Cloudflare-нонс щозапиту (§1.3), тож прив'язка блоба до сирих байтів створювала б новий 90-KB файл на кожному прогоні для сторінок, у яких насправді **нічого** не змінилось — ~2 GB/добу сміття, у якому справжня зміна губиться. Зміна, яку видно людині, завжди зачіпає `signals` або `text`, тож жодна реальна редакція коду не пропадає;
- сирий `raw_sha256` при цьому **все одно записується у версію** — тобто факт «байти відрізнялись» лишається в історії навіть тоді, коли ми не тримаємо для них окремий файл;
- дедуплікація за `sha256`: сторінка, що повернулась до попереднього вигляду, не створює третьої копії — версія просто посилається на вже наявний блоб;
- **`monitor_body_retention_days = 0` (зберігати вічно)** — дефолт саме такий, бо ретенція суперечила б вимозі «зберігати всі дані». `monitor-prune` (§3.9) прибирає **лише** блоби, на які не посилається жодна версія, і без явного прапорця не чіпає нічого іншого. Диск під контролем через лічильник у `monitor_runs` і `monitor-status`.

### 3.3 Що саме перевіряється

**Легка перевірка (щогодини, ~30–40 запитів на клієнта, ~30 с на весь портфель):**

1. robots.txt — повний фетч + семантичний розбір;
2. sitemap-індекс і вкладені файли — **тільки перелік URL і `lastmod`**, без обходу сторінок;
3. **ключовий набір сторінок**: головна + до 10 топ-сторінок за кліками GSC (§1.5) + усі сторінки, на яких минулий прогін лишив відкритий `critical` (доки не полагодять — дивимось щогодини);
4. DNS: `A`, `AAAA`, `CNAME`, `NS`, `MX`, `TXT`, `CAA` через два DoH-резолвери;
5. верифікації Google: TXT `google-site-verification=…`, HTML-мета `google-site-verification`, GA4 `G-…`, GTM `GTM-…` на ключових сторінках.

**Повна перевірка (що 3 години):** усе вищеперелічене плюс

6. **усі без винятку URL із sitemap** ∪ раніше відомі URL, які ще не «протухли» (див. нижче) — вимога користувача, підтверджена 2026-08-11;
7. точки входу: `http://apex`, `https://apex`, `http://www`, `https://www` — повний ланцюжок редіректів (трейсер task-29);
8. термін дії TLS-сертифіката (stdlib `ssl`).

**«Усі» означає всі — але прогін має закінчуватись.** `monitor_max_urls_per_client` лишається, проте вже не як продуктова межа, а як **аварійний клапан** із дефолтом 25 000 (найбільший клієнт зараз — 608): він існує тільки щоб зациклений або зіпсований sitemap не підвісив рушій назавжди. Друга межа — часова, `monitor_run_max_minutes` (дефолт 90).

Якщо якась із меж таки спрацює, прогін **не** починає наступного разу з початку списку (інакше хвіст sitemap не перевірявся б ніколи). Замість цього — **кільцевий обхід**: URL беруться в порядку

1. ключові сторінки (головна + топ-GSC) — завжди,
2. сторінки з відкритим `critical`/`warning` — завжди,
3. решта — за зростанням `last_checked_at`, тобто найдавніше перевірені першими.

Прогін чесно позначається `truncated`, у `monitor_runs` пишеться, скільки URL лишилось на наступний раз, а в API/UI видно «checked N of M». Мовчазної втрати даних немає (PLAN §12).

**URL, що зник із sitemap, не забувається одразу**: він лишається у списку перевірки ще `gone_retention_days` (дефолт 30) із позначкою `gone_since`. Саме так ловиться «сторінку видалили» — інакше видалена сторінка просто беззвучно зникла б зі спостереження, і 404 ніхто б не побачив.

**Робимо запит як робот, а не як людина:** ідентифікований UA (`…TheYovthClientPulse/1.0`, уже в `http_safety`), без cache-buster (нам треба бачити рівно те, що бачить Googlebot з CDN), з `Accept-Encoding: gzip`. Тіло читається з обмеженням (`max_body_bytes`, дефолт 3 MB) — сторінка-монстр не має ронять прогін.

**Свій robots.txt ми свідомо не виконуємо** (`monitor_respect_robots = false`): моніторимо сайти клієнтів за їхньою згодою, і момент, коли robots.txt закриває сайт, — це рівно той інцидент, який ми зобов'язані побачити й показати. Виконувати заборону, яка сама є предметом нагляду, — логічна пастка. Рішення явне, налаштовується, і `Crawl-delay` при цьому **поважається** (беремо `max(crawl_delay, 0.25 с)`).

### 3.4.1 Окреме правило: URL у sitemap зі статусом ≠ 200

Вимога користувача (2026-08-11), і вона потребує власної механіки, бо це **стан**, а не подія: 40 битих URL можуть лежати в sitemap місяцями й ніколи «не змінюватись».

- **Що вважається дефектом.** Будь-який URL, оголошений у sitemap, фінальний статус якого ≠ `200`. Розрізняємо три випадки, бо вони означають різне:
  - `3xx` → `sitemap_url_redirects` (**warning**): sitemap має містити кінцеві URL. Окремо мітимо суто нормалізаційні редіректи (`http→https`, `www`, слеш) — вони теж дефект, але спокійніший, тому йдуть з ознакою `normalization_only`.
  - `4xx` → `sitemap_url_broken` (**warning**, або **critical** якщо це ключова сторінка).
  - `5xx` / таймаут → `sitemap_url_unavailable` (**warning**; два прогони поспіль → **critical**, бо це вже не збіг).
- **Зведення замість спаму, з порогами, каліброваними по живих даних.** Вибірка 2026-08-11 (по 40 випадкових URL із sitemap чотирьох клієнтів): `hearwellservices` 0/40, `nysapphire` 0/40, `alphastyle` 0/40, **`exxxoticaexpo` 2/40** — обидва `301` на **іншу** сторінку (`/appearances/calliecadexxx/` → `/appearances/`), тобто видалені сторінки, які досі оголошені в sitemap. Екстраполяція — ~30 таких URL із 608 (~5 %). Це саме той випадок, який має бути **видимим, але не червоним**, тому рівнів зведення два:
  - `warning`, якщо частка ≥ `monitor_sitemap_broken_warn_pct` (2 %) або кількість ≥ `monitor_sitemap_broken_warn_count` (10) — сьогоднішній `exxxoticaexpo` потрапляє сюди;
  - `critical`, якщо частка ≥ `monitor_sitemap_broken_alert_pct` (10 %) або кількість ≥ `monitor_sitemap_broken_alert_count` (50) — це вже «sitemap масово бреше».

  Зведення несе розкладку за типами й до 10 прикладів URL — замість 30 окремих рядків у стрічці.
- **Це видно вже на baseline.** Загальне правило «перший прогін не алертить» стосується *змін*; стан «у sitemap 40 битих URL» оператор має побачити з першого ж прогону. Тому на baseline зведення `sitemap_broken_urls` **створюється**, а окремі URL пишуться в стан і в таблицю сторінок без 40 записів у стрічці.
- **Живий лічильник.** `GET /clients/{id}/monitor` завжди несе `sitemap_health` (`total`, `ok`, `redirects`, `broken`, `unavailable`) — щоб стан читався без археології по стрічці.
- **Самозагасання** працює як усюди: URL повернувся в `200` → відповідний запис отримує `resolved_at`.

`warning` — «змінилось те, що впливає на видачу»: `canonical_changed`, `title_changed`, `description_changed`, `h1_changed`, `page_status_error` (окрема сторінка 4xx/5xx), `page_redirect_appeared`, `page_gone`, `sitemap_urls_removed` (≥ `sitemap_drop_alert_pct`, дефолт 10 % або ≥ 10 URL), `robots_rules_changed`, `dns_txt_changed`, `dns_mx_changed`, `tls_expiring_14d`, `monitor_blocked` (WAF/челендж — окремий чесний стан, а не фальшиве «сайт ліг»).

`info` — «зафіксовано для історії»: `page_new`, `content_changed` (змінився `text_sha256`), `sitemap_lastmod_changed`, `robots_comment_changed`, `analytics_tag_added`, `robots_missing` (404), `page_body_changed` (тільки `raw_sha256`).

**Самозагасання.** Коли причина зникає (`noindex` прибрали, верифікація повернулась, сайт піднявся), відкритий запис отримує `resolved_at` і в стрічку дописується `info`-подія `<type>_resolved`. Без цього червоний бейдж горів би вічно й оператор перестав би на нього дивитись. `acknowledged_at` — окреме, ручне: «я бачив» ≠ «полагоджено».

**Перший прогін клієнта нічого не алертить.** Він створює baseline; порівнювати нема з чим, і 2 850 записів «нова сторінка» в перший день зробили б стрічку непридатною. У журналі це видно як `baseline` у `monitor_runs.notes_json`.

### 3.6 Планувальник

Потік у worker-процесі (PLAN §14 прямим текстом дозволяє «scheduler loop усередині єдиного worker»; окремий сервіс дав би другого писача в SQLite — саме те, чого PLAN §5.1 забороняє).

- тік раз на хвилину; для кожного клієнта рахує `due` як `останній_прогін(kind).started_at + інтервал`;
- **джитер**: зсув `sha1(client_id) % 20` хвилин — 14 клієнтів не стартують в одну секунду й не роблять залпу по 14 сайтах;
- **дедуплікація** (PLAN §16 «Етап 8» вимагає її явно): не ставимо light, якщо full цього клієнта зараз біжить (full його покриває); не ставимо другий прогін того ж kind, якщо попередній ще `running`; ручний «Check now» скидає таймер відповідного kind;
- **пауза клієнта**: `list_collectable()` (task-34) → паузовані з розкладу випадають; вмикається назад тумблером `monitor_settings.monitor_when_paused` на конкретного клієнта (підтверджено користувачем 2026-08-11). `enabled = false` вимикає завжди;
- **паралельність**: `monitor_client_workers` (дефолт 4) потоків, кожен веде одного клієнта від початку до кінця; всередині клієнта — послідовно з `HostThrottle`. Виміряні 10–12 хв на повний прогін — саме звідси;
- **після рестарту**: прогони, що лишились `running` довше за `monitor_run_stale_minutes` (дефолт 60), позначаються `failed_interrupted`; нічого не «відновлюється» — наступний тік перевірить те саме заново (§3.1);
- **зупинка**: `stop_event` перевіряється між URL, тож SIGTERM не чекає кінець обходу.

Проводка — один блок у [worker.py](../../../app/jobs/worker.py) (зона task-05, точковий дотик, задокументувати в Completion report — прецедент task-21). Без нього рушій є, але ніколи не стартує.

| `PATCH` | `/clients/{id}/monitor/settings` | Налаштування монітора клієнта |
| `GET` | `/clients/{id}/monitor/export.{csv,xlsx}` | Експорт сторінок і змін (`openpyxl`, як task-26/27) |

**Іменування, щоб не зіткнутися з task-17.** У проєкті вже є `/clients/{id}/alerts` — це алерти просідання трафіку GSC. Монітор **не** використовує слово `alerts` у шляхах і DTO: у нього `changes` із полем `severity`. Правило «одна назва — одна річ скрізь» (CLAUDE.md) зберігається.

### 3.9 CLI (`app/cli.py`, адитивно — зона task-07, задокументувати)

- `yovth-report monitor-run --client-id … --kind full|light [--all]` — разовий прогін без чекання розкладу;
- `yovth-report monitor-status [--severity critical]` — таблиця стану портфеля; ненульовий exit code за наявності відкритих `critical` (щоб оператор міг повісити власне сповіщення, доки немає каналів доставки);
- `yovth-report monitor-prune [--dry-run]` — прибирання блобів, **на які не посилається жодна версія** (осиротілі після ручного видалення рядків). Історію не чіпає: збережений код сторінок живе безстроково (§3.2.1). Видалення за віком — лише явним `--bodies-older-than <днів>`, і команда спершу друкує, скільки версій втратять тіло.

## 5. Тести

**Unit (`tests/unit/monitor/`):**

- `test_robots.py` — групи UA, інлайнові коментарі (`Disallow: /wp- # …`), wildcard, `Crawl-delay`, `Sitemap`; **регресія з живих даних:** `Disallow: /` для `meta-externalagent` ≠ `robots_blocks_site`, а той самий рядок для `*` = `critical`.
- `test_sitemaps.py` — index→children, `.gz`, циклічне посилання, аварійний клапан із `truncated`, діф множин URL, **кільцевий обхід** (після зрізаного прогону наступний починає з найдавніше перевірених, а не з початку списку).
- `test_sitemap_health.py` — правила §3.4.1: `3xx`/`4xx`/`5xx` дають різні типи; `normalization_only` для `http→https`/слеша; ключова сторінка ескалює до `critical`; зведення `sitemap_broken_urls` спрацьовує на порозі й **не** дублюється записами на кожен URL; на baseline зведення є, а 40 окремих записів у стрічці — немає; повернення в `200` ставить `resolved_at`.
- `test_page.py` — `noindex` у meta й окремо в `X-Robots-Tag`; `googlebot`-специфічна директива; canonical (self/off-site/відсутній); витяг `G-…`, `GTM-…`, `google-site-verification`; биті теги.
- `test_fingerprint.py` — **регресія з живих даних:** два тіла, що відрізняються лише `__CF$cv$params={r:'…'}`, дають однакові `signals_sha256` і `text_sha256`.
- `test_dns.py` — розбір DoH-відповіді, множинні verification-TXT, зникнення токена, розбіжність двох резолверів.
- `test_severity.py` — таблиця §3.4 повністю, включно з самозагасанням і «перший прогін не алертить».
- `test_scheduler.py` — `due`-логіка, джитер, дедуплікація light-під-full, паузований клієнт, `monitor_when_paused`.
- `test_storage.py` — дедуплікація однакових байтів, gzip, відмова на вихід за artifacts root; **baseline зберігає тіло кожної сторінки**; прогін без змін не створює жодного нового блоба навіть якщо сирі байти відрізняються (кейс Cloudflare-нонса); повернення сторінки до попереднього вигляду переюзує наявний блоб.

**API (`tests/unit/api/test_monitor_api.py`):** кожен ендпоінт §3.8 — включно з «клієнта не існує» (404), «прогонів ще не було» (порожній чесний стан, не 500), дифом між версіями та ack.

**Integration (`tests/integration/test_monitor_end_to_end.py`):** локальний `http.server` як фейковий сайт клієнта, чотири послідовні прогони — (1) baseline (у sitemap одразу є один `404`-URL), (2) підміняємо головну на `noindex` + прибираємо TXT-верифікацію + прибираємо URL із sitemap, (3) ламаємо ще 30 % URL sitemap до `404`/`500`, (4) повертаємо все як було. Перевіряємо: на першому — жодної зміни, але **є** зведення `sitemap_broken_urls` і збережене тіло кожної сторінки; на другому — `critical` × 2 + `warning`; на третьому — ескалація зведення до `critical` без спаму на кожен URL; на четвертому — `resolved_at` скрізь; ланцюг версій цілий; незмінені сторінки **не** створили ні версій, ні блобів.

**Live (`tests/live/`, лише з `--live`):** один light-прогін по реальному клієнту — перевіряє, що DoH відповідає, robots парситься, ключові сторінки віддають сигнали.

Обов'язково в Docker: `docker compose exec api poetry run pytest tests/unit/monitor tests/integration/test_monitor_end_to_end.py -q`, далі `ruff check .` і `mypy app`.

## 6. Ризики та запобіжники

| Ризик | Запобіжник |

Важелі інші: `full_interval_hours` на клієнта, `If-None-Match`/`If-Modified-Since` там, де сервер їх підтримує, і **чесний лічильник байтів у кожному прогоні** — щоб ціна була видима, а не сюрпризом у рахунку |

| **Ріст диска** — код сторінок зберігається безстроково (§3.2.1) | Baseline ≈250 MB одноразово; далі новий блоб лише на реальну зміну + дедуплікація за `sha256`. | **Конкуренція за запис у SQLite з worker-ом** | Короткі транзакції, пачка на клієнта в кінці, WAL уже увімкнений; монітор пише **тільки у власні таблиці** |
| **Шум у стрічці** | «Перший прогін = baseline», самозагасання, `muted_change_types` на клієнта, `info` за замовчуванням згорнутий (task-36) |
| **Збережений HTML клієнта — це його дані** | Лежить під artifacts root із перевіркою шляху, віддається тільки через API застосунку; у логах — лише хост (PLAN §13), SSRF-гард на кожен запит і кожен редірект |
| **DoH-резолвер недоступний** | Два резолвери; якщо обидва мовчать — прогін фіксує `dns_unavailable` як `warning` і **не** трактує це як зникнення записів (`None` ≠ «немає», PLAN §12) |
