### §0.2 `synchronous=FULL` коштує ~70× на кожному коміті

Бенчмарк на **копії бойової бази**, у контейнері, 200 послідовних однорядкових комітів, двічі поспіль:

```
synchronous=FULL:    200 commits in 285ms  ->  1.42 ms/commit
synchronous=NORMAL:  200 commits in   4ms  ->  0.02 ms/commit
synchronous=FULL:    200 commits in 306ms  ->  1.53 ms/commit
synchronous=NORMAL:  200 commits in   5ms  ->  0.02 ms/commit
```

**~70×.** А оскільки коміт відбувається **всередині** утримуваного writer-лока, це ×70 не до «швидкості запису», а до **часу, протягом якого всі інші стоять**.

### §0.3 Writer-лок зайнятий 97% часу під час бурсту

Проба `BEGIN IMMEDIATE` з `busy_timeout=0` кожні 100 мс, 30 с, під час звичайної роботи (archive-capture + cloud-sync):

```
30s sample: write lock AVAILABLE 8/300 (3%), BUSY 292/300 (97%)
acquire time when free: p50=0.05ms  max=0.1ms
```

Другий замір, уже **після** рестарту воркера й поза бурстом, 20 с з кроком 10 мс:

```
busy periods: n=55  total=1.5s  longest=0.98s
free windows: n=55  total=18.5s longest=1.21s      # ~8% busy
```

Висновок однозначний: **проблема не в SQLite і не в тривалості одного запису (0.05 мс на взяття лока), а в кількості й некоординованості записувачів під час бурсту.**

### §0.4 Скільки нас насправді пише — і чому 30-секундний `busy_timeout` це підсилювач

Потенційні одночасні DB-потоки в **одному** worker-процесі (`app/core/config.py`):

| Планувальник | Потоків |
|---|---|
| `monitor_client_workers` × `monitor_page_workers` | 16 × 6 = **до 96** |
| `archive_client_workers` × `archive_page_workers` | 6 × 4 = **24** (записи серіалізовані `ArchiveWriteController`) |
| `reports_api_workers` + `reports_batch_client_workers` + `reports_pdf_workers` | 3 + 3 + 1 = 7 |
| `cloud_upload_workers` | 4 |
| `jobs.dispatcher` (доріжки провайдерів) | 12 |

Плюс **api-процес**: `anyio` threadpool = **40** потоків (виміряно живо), кожен `def`-ендпойнт і кожен `run_in_threadpool` бере з нього слот. Плюс разові CLI-процеси.

А пули такі (виміряно живо через `get_sync_engine().pool`):

```

async pool: AsyncAdaptedQueuePool size=5  max_overflow=10
anyio default thread limiter: 40 tokens
```

Тобто **до ~140 потоків претендують на 15 з'єднань**, і той, кому не вистачило, чекає **30 с** (`pool_timeout`), а той, хто пише і не дістав лок, чекає ще **30 с** (`busy_timeout`). Один застряглий записувач тримає з'єднання пулу пів хвилини → **отруює весь пул** → кожен наступний запит, навіть чисте читання, стає в чергу. Це і є механіка «27 секунд і біла сторінка»: не одна повільна відповідь, а каскад.

Вимір деградації пулу (80 паралельних читань з утриманням з'єднання 50 мс):

```

concurrency= 15  wall=  68ms  p50= 63.0ms  max= 65.0ms
concurrency= 40  wall= 162ms  p50=101.9ms  max=155.0ms
concurrency= 80  wall= 306ms  p50=158.1ms  max=295.6ms
```

Читання чітко йдуть **хвилями по 15** — рівно розмір пулу. Поки утримання коротке (50 мс), це терпимо; щойно утримання стає секундами — це смерть.

## §1. Фаза A — дешеві структурні виправлення DB-шару

> Оцінка: найбільший ефект на одиницю ризику. Робиться першою і **міряється окремо**, щоб було видно, скільки взагалі лишилося проблеми для §2.

### §1.1 `synchronous=NORMAL` + решта PRAGMA

`app/db/session.py`, `_apply_sqlite_pragma`:

```python
cursor.execute("PRAGMA journal_mode=WAL")
cursor.execute("PRAGMA foreign_keys=ON")
cursor.execute("PRAGMA synchronous=NORMAL")      # 1.42ms -> 0.02ms на коміт (§0.2)
cursor.execute("PRAGMA temp_store=MEMORY")
cursor.execute(f"PRAGMA cache_size={-settings.sqlite_cache_kib}")   # дефолт 65536 = 64 МБ
cursor.execute(f"PRAGMA mmap_size={settings.sqlite_mmap_bytes}")    # дефолт 268435456 = 256 МБ
cursor.execute(f"PRAGMA busy_timeout={...}")     # див. §1.3 — різний для read і write
```

**Компроміс `synchronous=NORMAL`, чесно.** У WAL це офіційно рекомендований режим і він **не може пошкодити базу**. Єдиний ризик — за раптового зникнення живлення / паніки ядра (не за краху застосунку!) можна втратити **останні кілька транзакцій**. Для внутрішнього дашборда з щодобовим бекапом у B2 (task-52) це прийнятна ціна за ×70. Рішення свідоме й записується в Completion report.

### §1.2 Розділити read-engine і write-engine

Зараз усі — читачі й записувачі, api й воркер — б'ються за один пул на 15 з'єднань. WAL дозволяє **необмежену кількість паралельних читачів**; штучно обмежувати їх п'ятнадцятьма — наша власна вигадка.

Нове в `app/db/session.py`:

| Engine | Пул | Навіщо |
|---|---|---|
| **read** (sync) | `pool_size=48, max_overflow=16, pool_timeout=5` | покриває 40 anyio-потоків із запасом; WAL-читачі одне одному не заважають |
| **read** (async/aiosqlite) | `pool_size=16, pool_timeout=5` | лишається для `get_db()`-ендпойнтів |
| **write** | `pool_size=1, max_overflow=0` | **структурна гарантія**: у процесі фізично не існує двох записувальних з'єднань |

`pool_timeout` падає 30 → **5 с**. Насичений пул мусить швидко віддати чесну помилку, а не тримати вкладку білою пів хвилини.

`pool_size=1` на write-engine — не оптимізація, а **інваріант**: після §2 писати має право лише потік gate'а, і пул це унеможливлює порушити навіть випадково.

### §1.3 `busy_timeout` — різний і набагато менший

- **read-з'єднання:** `busy_timeout=5000`. Читач у WAL взагалі не мав би упиратись у лок; якщо впирається (чекпойнт) — 5 с з головою.
- **write-з'єднання (потік gate'а):** `busy_timeout=10000`. Після §2 конкуренцію вже розв'язав gate; будь-який SQLITE_BUSY тут означає **чужого записувача в обхід gate'а** — це баг, і він має впасти швидко й голосно, а не мовчки чекати 30 с.

`SQLITE_BUSY` перестає бути «нормою життя» й стає сигналом дефекту. Це окремий DoD-пункт (§6).

### §1.4 `ANALYZE` + `PRAGMA optimize` (`sqlite_stat1` порожня!)

Планувальник вибирає між 3–4 індексами на гарячих таблицях **без жодної статистики**. Нова CLI-команда:

```bash
docker compose exec api poetry run yovth-report db-maintenance   # ANALYZE + wal_checkpoint(TRUNCATE) + optimize
```

Плюс `PRAGMA optimize` на закритті з'єднання (стандартна рекомендація SQLite) і виклик `db-maintenance` з `CloudScheduler` раз на добу поруч із бекапом.

## §2. Фаза B — один глобальний обробник записів (`DbWriteGate`)

Це те, що просив користувач: **усі записи йдуть через одну чергу**. Ключове доповнення до task-62: чергу треба зробити не «одну на процес», а **одну на систему**, бо api і worker — різні OS-процеси, і `ArchiveWriteController` між ними нічого не координує (його власний docstring це чесно визнає).

### §2.1 Конструкція: черга в процесі + `flock` між процесами

Новий `app/db/writegate.py`:

```
[N потоків процесу] → черга (1 потік-обробник на процес) → flock(app_data/db.write.lock) → BEGIN IMMEDIATE … COMMIT
```

Два рівні, і кожен закриває те, чого не може інший:

1. **Внутрішньопроцесний рівень** — узагальнений `ArchiveWriteController`: одна `queue.Queue`, один демон-потік, виклик через `Future`. Викликач блокується на своєму `Future`, **не** на SQLite. Мережевого I/O в задачі бути не може (§2.3).
2. **Міжпроцесний рівень** — `fcntl.flock(LOCK_EX)` на `app_data/db.write.lock`, береться потоком-обробником **безпосередньо навколо** `BEGIN IMMEDIATE … COMMIT` і одразу віддається.

Разом: у будь-який момент у всій системі виконується **рівно одна** записувальна транзакція. Черга вибудовується в **ядрі на flock**, а не в сліпому polling-циклі `busy_timeout`, тож зникає і `database is locked`, і 30-секундні хвости, і `commit_with_retry`-шторми.

**Чому `flock`, а не окремий writer-сервіс:** нуль нових процесів, нуль нових залежностей, нуль мережевого хопу, працює для разових CLI-запусків «безкоштовно» (той самий файл), знімається ядром автоматично при вбитому процесі — тобто мертвий лок неможливий структурно. Ціна: `flock` на Linux не дає гарантії FIFO-справедливості. При наших 2–3 процесах це не проблема, але §6 має пункт про вимір голодування.

### §2.2 API — навмисне сумісний із task-62

```python
gate = get_write_gate()
result = gate.submit(session, fn)          # той самий підпис, що ArchiveWriteController.submit
```

`app/webarchive/writequeue.py` стає **тонким shim**: `ArchiveWriteController` делегує в глобальний gate. Жоден із ~20 наявних викликів у `capture.py` / `scheduler.py` / `cloud_sync.py` не переписується — і це головна причина обрати саме такий підпис. Deprecation-нотатка в docstring, фізичне видалення — окрема прибиральна таска.

### §2.3 Інваріант «жодного I/O під локом» — тепер такий, що його видно

`db_retry.py` уже просить «Never call this before network I/O», але це лише коментар, який task-65 ловить руками вже вдруге. У gate це стає **виконуваним**:

- `submit()` міряє тривалість `fn()` і **логує WARNING** із стеком, якщо задача триває довше за `db_write_gate_slow_ms` (дефолт 250 мс) — довга задача під глобальним локом майже завжди означає I/O всередині.
- У тестах — hard-fail замість warning (`YOVTH_WRITE_GATE_STRICT=1`), щоб регресія падала в CI, а не через місяць у продакшені.

### §2.4 `commit_with_retry` різко спрощується

Після §2 конкуренцію розв'язано **до** SQLite, тож ретраї з розкладом `(1.0, 5.0, 15.0, 30.0)` с — це решта старої моделі. Схема стає `(0.05, 0.2, 0.5)` і трактується як «щось пішло в обхід gate'а — залогуй голосно». Сам файл `db_retry.py` лишається (його імпортують `capture.py`/`cloud_sync.py`, чужі owned paths), змінюється лише розклад і docstring.

## §4. Фаза D — libSQL / Turso: експеримент за бенчмарк-гейтом

Користувач попросив явно — тому це в плані як **вимірюваний крок**, а не як «подивимось».

### §4.1 Що це реально дає (станом на 2026-09)

- **`sqlalchemy-libsql`** — офіційний діалект, тепер живе в `tursodatabase/libsql-sqlalchemy` (старий `libsql/sqlalchemy-libsql` заархівовано 2025-06-11). Статус: **Beta** (`Development Status :: 4`), тягне `libsql-experimental>=0.0.53`, `sqlalchemy>=2.0`, `greenlet`.
- **Turso Database** (переписаний на Rust) — саме він дає **MVCC / `BEGIN CONCURRENT`** через `PRAGMA journal_mode='mvcc'`: рядковий рівень конфліктів, конфлікти перевіряються на коміті, **`SQLITE_BUSY` зникає як клас**. Заявлено ~**4× write throughput** проти SQLite на 8 потоках. У v0.5 фіча перейшла з tech preview у **beta** («limited production use»); у Turso Cloud — early preview з 2026-08-03.
- **Сумісність із нашим образом перевірена живо:** `libsql_experimental-0.0.55-cp312-cp312-manylinux_2_17_x86_64.whl` завантажується й ставиться (образ = Python 3.12.12).

### §4.2 Чесна оцінка застосовності саме тут

Ключове, що видно з §0: **наше вузьке місце — не пропускна здатність SQLite, а те, що ми самі себе не координуємо.** Лок береться за 0.05 мс, читання швидкі. Тому очікуваний виграш від libSQL **після** §1+§2 — швидше за все **близький до нуля**, а ризик — реальний: beta-двигун під 761-МБ бойовою базою, beta-діалект, і окремо треба переперевірити alembic, `scripts/backup_sqlite.py`, `scripts/restore_sqlite.py` та B2-офсайт (task-52).

Тому §4 будується так, щоб **або дати виміряний виграш, або бути викинутою за півгодини**:

1. `scripts/db_bench.py` (пишеться в §1, ним же міряються §1 і §2) відтворює наш **власний** бурст: 6 archive-потоків × 4 сторінки + cloud-sweep + 40 паралельних replay-читань.
2. Прогін на **копії** бойової бази у трьох конфігураціях: `baseline` → `A+B` → `A+B+libsql`.
3. Драйвер обирається налаштуванням `database_driver: "pysqlite" | "libsql"` — тобто це **перемикач, а не міграція**. Файл бази той самий, формат сумісний, відкат = зміна одного рядка в `.env`.
4. **Gate:** libSQL лишається, тільки якщо дає **≥2×** до `A+B` на p95 запису **і** вся тестова сюїта зелена **і** `alembic upgrade head` + backup/restore відпрацювали на копії. Інакше — фіксуємо числа в Completion report і закриваємо як «не потрібно».

**MVCC-режим (`journal_mode='mvcc'`) у цю таску не входить взагалі.** Він у beta й вимагає окремого двигуна Turso Database — це предмет майбутньої таски, і **тільки** якщо §4.1 покаже, що звичайного libSQL мало.

⚠️ Нові залежності = **запит до task-01** (CLAUDE.md). Робиться лише після проходження gate'а, не «про запас». Пам'ятка: `poetry lock` у цьому середовищі падає без сусіднього checkout'у AISeoTools — це окремий крок, який треба закласти в §4.

## §5. Відкинуті альтернативи

| Варіант | Чому ні |
|---|---|
| **PostgreSQL** | Розв'язав би все — але це новий сервіс, повна переміграція 761 МБ / 52 таблиць, зміна бекап-стратегії (task-52), і DevOps під внутрішній інструмент на одному сервері. §0 показує, що ми ще навіть не вичерпали SQLite: 97% зайнятості лока — наша власна некоординованість, а не стеля двигуна. Тримаємо як план B із **чітким тригером**: якщо після §1+§2+§3 writer-лок і далі >40% зайнятий на бурсті — це вже стеля, і тоді Postgres обґрунтований. |
| **Просто підняти `busy_timeout`** | Рівно навпаки: 30 с уже зараз **підсилює** аварію (§0.4). Треба зменшувати, а чергу будувати явно. |
| **Окремий writer-сервіс (RPC)** | Дає те саме, що `flock`, ціною нового процесу, нового протоколу, нового класу відмов і мережевого хопу на кожен запис. `flock` дає ту саму гарантію в ~80 рядках і знімається ядром при вбитому процесі. |
| **`SingletonThreadPool` / `StaticPool` замість черги** | Обмежує з'єднання, але не впорядковує записувачів і взагалі не бачить іншого процесу. Не розв'язує задачу. |
| **Шардинг archive у власний файл БД** | Прибрав би найгучнішого записувача з-під ніг у решти — але ламає FK на `clients`, крос-модульні джойни й одну точку бекапу. Розглядати лише якщо §1+§2+§3 не вистачить, і тоді радше вже Postgres. |
| **`PRAGMA synchronous=OFF`** | Ще швидше за NORMAL, але **може пошкодити базу** при втраті живлення. NORMAL у WAL — не може. Різниця в ризику непорівнянна з різницею у швидкості (0.02 мс уже й так дно). |

## §6. Definition of Done / Gate

Кожен пункт — вимірюваний, з базовою лінією з §0.

1. **Writer-лок під бурстом < 40% зайнятості** (базова лінія **97%**). Міряти тим самим 30-секундним пробником із §0.3 під час реального archive-capture.
2. **Нуль `database is locked` в api-процесі за 24 год** (базова лінія **292**). Будь-яке одне таке спрацювання після §2 — це записувач в обхід gate'а, тобто баг, а не шум.
3. **Нуль `archive_blob_upload_failed error=OperationalError`** за повний cloud-sweep (зараз падає регулярно).
4. **`synchronous=NORMAL` підтверджено живим `PRAGMA`-читанням** у обох контейнерах, і `scripts/db_bench.py` показує ≤0.1 мс/коміт (базова лінія 1.42 мс).
5. **`sqlite_stat1` існує й непорожня** після `db-maintenance`; команда є в CLI й викликається зі щодобового тіка.
6. **Пули розділені**: живе читання `get_read_engine().pool` / `get_write_engine().pool` показує `48/16` і `1/0` відповідно; `pool_timeout=5`.
7. **Інваріант gate'а виконуваний**: тест, у якому задача `submit()` робить `time.sleep(0.5)`, падає при `YOVTH_WRITE_GATE_STRICT=1`.
8. **Немає голодування**: `db_bench.py` під 3 процесами показує p99 очікування в черзі запису < 2 с.
9. **§4 закритий числом**: у Completion report є таблиця `baseline / A+B / A+B+libsql` і явне рішення «беремо / не беремо» з обґрунтуванням.
10. **Список 7 блокувальних `async def`** зафіксовано в Completion report як follow-up із власником (не правимо чужі owned paths у цій тасці).
11. `ruff` + `mypy app` + повна `pytest`-сюїта зелені **в Docker**.
12. **Перед першим прогоном на бойовій базі — бекап** (CLAUDE.md): `docker compose exec api poetry run python scripts/backup_sqlite.py --out-dir /app/app_data/backups --keep 14`.

## §7. Тести

- `tests/unit/db/test_session_pragmas.py` — кожен PRAGMA справді застосований на **новому** з'єднанні обох engine'ів; read і write мають **різні** `busy_timeout`; write-пул фізично не віддає друге з'єднання.

- `scripts/db_bench.py` — не pytest, а відтворюваний харнес для §6; його вивід іде в Completion report.

## §8. Ризики

| Ризик | Мітигація |
|---|---|
| `synchronous=NORMAL` — втрата останніх транзакцій при зникненні живлення | Свідомий компроміс, задокументований; щодобовий B2-бекап (task-52) уже є. Пошкодження бази неможливе — це властивість WAL, не наша обіцянка. |
| `flock` не FIFO → голодування процесу | DoD #8 міряє p99 очікування. Якщо спливе — черга в самому gate стає впорядкованою по timestamp (запас за конструкцією). |
| Хтось пише повз gate і ловить швидкий SQLITE_BUSY замість 30-секундного очікування | Це **мета**, а не побічний ефект: голосний WARNING зі стеком (§2.3) показує рівно те місце, яке треба завести в gate. |
| Колізія з активною task-65 | §3 не починається до її закриття; §1/§2/§4 не торкаються її файлів. Перед комітом — `git status` на `capture.py`/`cloud_sync.py`/`web_archive.py` (той самий протокол, що вже спрацював у task-63). |
| libSQL beta пошкодить бойову базу | §4 працює **виключно на копії**; перемикач `database_driver`; бекап перед будь-яким дотиком (DoD #12). |
| `poetry lock` падає без сусіднього AISeoTools | Відомо (пам'ятка середовища). §1–§3 нових залежностей не мають узагалі; для §4 це окремий крок із запитом до task-01. |
