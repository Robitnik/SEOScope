## §0. Чому не Redis і не інша БД (виміряно 2026-09-06)

Розглядалася пропозиція винести навантаження в Redis: тримати там копію БД, писати паралельно, наприкінці зливати пачкою в SQLite. Ідею перевірено вимірюванням, а не міркуванням.

### §0.1 База вже цілком у RAM

```
app.db 762 MB -> resident in OS page cache 762 MB (100.0%)
```

Redis у ролі «завантажити БД у пам'ять» — це друга, гірша копія того, що ОС уже дала безкоштовно: без SQL, без планувальника, без транзакцій, за окремі 2–4 ГБ RSS. Це ж пояснює вимір task-66 §0.6, де `cache_size`/`mmap_size` не дали різниці (74.8 мс проти 72.6 мс).

### §0.2 Ми за чотири порядки від стелі запису

Бенчмарк на копії бойової бази (WAL + `synchronous=NORMAL`, один записувач) проти реального добового обсягу:

| | значення |
|---|---|
| Стеля одного записувача | **23 766 txn/s** (батчами — до 670 тис. рядків/с) |
| Фактично пишеться | 32 525 рядків/добу = **0.38 рядка/с** |
| Використання ємності | **0.0016 %** |

Уся денна робота із запису — приблизно **одна секунда**. Проблема ніколи не була в пропускній здатності.

### §0.3 Читачі не страждали ніколи

У бенчмарку з 6 паралельними записувачами, за зайнятості writer-лока 97–99%, читач стабільно давав `p50 = 0.06–0.14 мс` **у всіх стратегіях, на всіх ~10 прогонах**. WAL-читач не блокується записувачем. Отже «97% лок зайнятий» (task-66 §0.3) **не пояснює** повільний ендпойнт — це робив дедлок (§1) і наш власний flock на шляху читання (§3).

### §0.4 Батчинг: правильний за формою, але не там

3000 рядків у справжню `gsc_dimension_metrics` (5 індексів), паралельно читач і «інтерактивний» записувач:

| Стратегія | wall | інтерактивний WRITE p50 / p99 |
|---|---|---|
| коміт на кожен рядок | 668–1085 мс | 0.1 / **330–630 мс** |
| group-commit (200) | 594–643 мс | 0.1 / **33–53 мс** |
| усе накопичити → 1 коміт | **147–160 мс** | **103.5** / **310–330 мс** |
| те саме через JSON (проксі Redis) | 162–173 мс | 2.7–9.5 / 307–330 мс |

Висновки: bulk-коміт справді ×4.5 швидший, **але** один довгий неперервний хват б'є по інтерактиву сильніше, ніж багато коротких; а JSON round-trip (тобто вихід за межі процесу, як у Redis) стабільно **на 10–15 мс дорожчий** за звичайний список у пам'яті, з ідентичним профілем лока. Redis не купує нічого.

### §0.5 Справжній домінантний коштовний елемент — чекпойнт WAL

Аномалія: чанк 500 → 175 мс, чанк 200 → 582 мс. Причина знайшлася вимірюванням:

```
chunk=3000  autocheckpoint=1000   wall= 432ms   max_hold= 432.0ms
chunk=500   autocheckpoint=1000   wall= 512ms   max_hold= 351.4ms
chunk=200   autocheckpoint=1000   wall= 521ms   max_hold= 334.2ms
chunk=50    autocheckpoint=1000   wall= 571ms   max_hold= 343.9ms

chunk=3000  autocheckpoint=0      wall=  88ms   max_hold=  87.9ms
chunk=500   autocheckpoint=0      wall= 107ms   max_hold=  21.2ms
chunk=200   autocheckpoint=0      wall= 120ms   max_hold=  13.4ms
chunk=50    autocheckpoint=0      wall= 127ms   max_hold=   6.6ms
```

**×4–5 по wall і до ×50 по найдовшому хвату — від однієї PRAGMA.** Зі стоковим `wal_autocheckpoint=1000` той коміт, що випадково переповнив WAL, платить за копіювання WAL назад у базу, **тримаючи writer-лок 334–432 мс**. Розмір чанка на це майже не впливає — саме тому дрібніші чанки не допомагали.

**Це і є відповідь на «чому все стоїть при 0.38 запису/с»**, і саме цього Redis не чіпає: перенісши записи в Redis, фінальний злив у SQLite так само з'їв би цей чекпойнт.

## §1. Дедлок `DbWriteGate` — аварія 2026-09-06 ✅ done

### §1.1 Що сталося

Воркер замовк о `05:16:49`, одразу після `archive_scheduler_reclaimed_dead_captures count=5`. Кожен api-ендпойнт на синхронній сесії висів понад 90 с. `/proc/locks` показав:

```
206: FLOCK ADVISORY WRITE 43353   ← python -m app.jobs.worker (тримає)
206: -> FLOCK ADVISORY WRITE 42698 ← uvicorn (чекає)
44293 uvicorn wchan=locks_lock_inode_wait   ← потік db-write-gate api-процесу
```

Усі 40+ потоків воркера — у `futex_do_wait`, жодного I/O. Захват завмер на **0 URL**.

### §1.2 Механіка

Ланцюжок з чотирьох ланок, кожна сама по собі виглядає нешкідливо:

1. `worker_session_scope` віддає **будь-який** коміт (навіть no-op) у `get_write_gate().submit(...)`.
2. `DbWriteGate._process` тримає крос-процесний flock навколо `job.fn()` **і** `commit()`, а обробник — **один потік на процес**.
3. task-66 змінила `commit_with_retry` так, що в gate їде не лише коміт, а **весь `fn()`**.
4. `capture.py:813` передає туди `_capture_url_and_commit`, який **сам** викликає `write_controller.submit(...)` (`capture.py:687`, і ще раз на кожен asset — `capture.py:395`).

Отже потік gate'а виконує `fn()`, всередині якого `submit()` ставить задачу у **власну** чергу й чекає на `future.result()` — чекає сам на себе, **не відпускаючи flock**. Не гонка, а гарантований наслідок будь-якого gated `fn()`, який сам пише.

### §1.3 Виправлення

- **`DbWriteGate.submit` — реентрантність.** Якщо `threading.current_thread() is self._thread`, виконуємо `fn()` + `commit()` інлайн: flock уже тримається цим потоком, контракт «один запис за раз» уже виконано. Це не запасний шлях, а коректна семантика — результат такий самий, як без gate'а.
- **`commit_with_retry` — `fn()` на потоці викликача**, у gate їде лише коміт. Це відновлює інваріант, який `capture.py` і `cloud_sync.py` **уже документували** («only the actual commit is serialized») і який task-66 мовчки зламала. Без цього повний захват сторінки з усіма мережевими фетчами виконується під глобальним крос-процесним локом.

Обидві правки потрібні: друга робить так, щоб дедлок не виникав; перша — щоб цілий клас цієї помилки був структурно неможливим.

## §2. Чекпойнт WAL поза шляхом запису ✅ done

- `Settings.sqlite_wal_autocheckpoint = 0` + `PRAGMA wal_autocheckpoint` у `_apply_sqlite_pragma`. Числа — §0.5.
- **Чекпойнтер живе в потоці `DbWriteGate`**, бо це єдиний записувач процесу і єдиний, хто знає, коли черга порожня. `queue.get(timeout=db_checkpoint_idle_s)`; на `queue.Empty` — `_checkpoint()`.
- `wal_checkpoint(TRUNCATE)`, не `PASSIVE`: заміряно, що PASSIVE під живим трафіком лишає WAL на всі 85 МБ. TRUNCATE може бути заблокований довгим **читачем** — тоді це штатна ситуація, наступне вікно спробує знову (`db_write_gate_checkpoint_busy`, debug).
- Окреме короткоживуче з'єднання, а не з пулу: потрібен власний короткий `busy_timeout` (чекпойнт не сміє сидіти на читачі, поки за цим потоком копичаться задачі), а виставляти його на пуловому з'єднанні означало б протекти значення наступному користувачеві.
- Поріг `db_checkpoint_min_wal_mb` (4 МБ): потік прокидається кожні 2 с, і чекпойнтити майже порожній WAL — марна syscall-метушня.

**Чекпойнтер обов'язковий, а не опційний.** При `autocheckpoint=0` без нього WAL росте безмежно (виміряно 85 МБ на бурст у 4× добового обсягу). `sqlite_wal_autocheckpoint` лишено налаштуванням саме як аварійний відкат до поведінки SQLite без правки коду.

### §2.1 Чекпойнтер спершу сам став джерелом стопів (знайдено живою перевіркою)

Перша редакція ставила чекпойнту `busy_timeout=1000`. Під справжнім портфельним захватом це дало:

```
slow_job duration_ms=1012..1023 queue_wait_ms=4912..5002   (x21, усі у воркері)
```

Кожен із них — коміт воркера, що стояв за цим потоком, поки той **тримав крос-процесний flock і чекав на читача**. Тобто рівно той стоп, який ця таска прибирає, відтворений її ж власним виправленням. Знайдено лише живим прогоном — юніт-тести цього не ловлять.

Виправлення: `busy_timeout=0` (миттєво взяв або миттєво здався) + експоненційний backoff до 60 с на послідовних busy. Здатися — нормальний випадок, а не збій: читання ~4 мс, тож проміжки між ними часті, і чергове вікно в такий проміжок потрапляє.

Живе підтвердження після виправлення: `db_write_gate_checkpoint wal_mb=4.4 duration_ms=25`, WAL тримається на 3 МБ під навантаженням, `slow_job` — 0.

## §3. Read-only сесії не платять за write-лок ✅ done

Після §1 і §2 живі проби ще ловили сплески. Логи назвали винного:

```
db_write_gate_slow_job duration_ms=2686 queue_wait_ms=0 threshold_ms=250
db_write_gate_slow_job duration_ms=4901 queue_wait_ms=0 threshold_ms=250
```

`queue_wait_ms=0` кладе ці секунди **всередину очікування flock**, а не за іншими задачами в черзі. І це `GET /api/v1/monitor/changes` — ендпойнт, який не пише **нічого**: `worker_session_scope` гнав його no-op коміт через крос-процесний лок.

Виправлення — `session_has_pending_writes()`; обидва сигнали потрібні, живо перевірено на справжньому engine:

| що робила сесія | ORM staged | DBAPI `in_transaction` |
|---|---|---|
| нічого | False | False |
| SELECT (ORM або `text()`) | False | False |
| `execute(text("UPDATE"))` | False | **True** |
| `session.add(...)` | **True** | False |

pysqlite відкриває транзакцію лише на реальному DML і ніколи на SELECT — тому `in_transaction` ловить raw-`execute()` записи повз ORM, а `new/dirty/deleted` ловить застейджене ORM-написане, ще не злите в драйвер. Функція **зміщена в бік `True`**: `dirty` означає «можливо змінено», а незнайомий драйвер провалюється в `True`. Хибний позитив коштує зайвого проходу через gate; хибний негатив пустив би справжній запис повз серіалізацію — заради якої gate і існує.

### §3.1 Async-пул лишався нерозміреним

task-66 §1.2 планувала розміри для **обох** engine, але зробила лише sync: `build_async_engine` викликав `create_async_engine(url)` без аргументів, тобто стокові 5 + 10 і `pool_timeout=30` — і це саме та половина, що обслуговує кожен `async def`-ендпойнт, включно з `/dashboard`. Дороблено: `sqlite_async_pool_size=16`, `max_overflow=16`, спільний `sqlite_pool_timeout_s=5`.

З інтерфейсом `submit(rows)` / `submit(stmt, params)` мережевий I/O під локом і рекурсивний submit стають **структурно неможливими**, а не «виправленими». - **§5.3 Синхронні сесії з `async def`** — 7 місць (task-66 §0.6): `jobs.py` ×3, `client_monthly.py` ×2, `reports.py`, `url_inspector.py`. Другорядний борг, але після §3 це єдине, що лишилося блокувати event loop.

## §6. Definition of Done / Gate

1. ✅ Реентрантний `submit` не вішає gate і **відпускає flock** — два окремі тести, обидва з жорстким таймаутом (до фіксу вони не падають, а **зависають**).
2. ✅ `commit_with_retry` виконує `fn()` на потоці викликача — тест на ідентичність потоку (тест на *результат* проходить і зі зламаним кодом, саме так регресія й доїхала до прода).
3. ✅ `wal_autocheckpoint=0` за замовчуванням, відкат через налаштування — обидва напрямки в тестах.
4. ✅ Idle-чекпойнтер реально повертає WAL і **не втрачає рядків**; нижче порога не робить нічого.
5. ✅ Read-only сесія не позначається як така, що має записи; raw `execute(UPDATE)` — позначається.
6. ✅ **Живо**, не лише в тестах: `/api/v1/monitor/changes?...&limit=500&severity=critical` **60+ с → 0.055 с**; під час справжнього archive-capture проби тримаються **4–7 мс** (до §3 — сплески 2.7 с і 4.9 с); захват іде (100+ URL проти **0** за дедлоку), `database is locked` — **0** за 10 хв, `slow_job` після рестарту — **0**.
