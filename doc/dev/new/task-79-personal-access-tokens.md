- **Хвиля:** post-77, **перед** [task-78](task-78-mcp-remote-oauth-connector.md) — це його фаза A, винесена в окрему таску й перероблена з CLI на самообслуговування

## 0. Навіщо

Сьогодні bearer-доступ до API дає рівно один механізм — `AGENT_DEV_TOKEN` (task-73). Він навмисно зроблений так, щоб **не** годитись для людей:

- один секрет на всіх, тож журнал task-72 не може сказати, хто саме щось зробив;
- відкликати в однієї людини = поміняти всім;
- **структурно мертвий на `ENVIRONMENT=production`** — і це правильно, але означає, що в проді bearer-доступу зараз немає взагалі.

Водночас потреба вже є з трьох боків: MCP по HTTP (task-78), скрипти й CI, і просто `curl` у прод без копирсання в cookie. Спільний секрет на це не розтягнеш.

**Що дає ця таска:** кожен користувач заходить у свій кабінет, натискає «New token», отримує значення **один раз** і використовує його як `Authorization: Bearer …`. Токен несе **його** особу і **його** роль.

⚠️ **Чого вона НЕ дає, щоб не було ілюзій:** сама по собі вона не вмикає claude.ai. claude.ai потребує HTTP-транспорту й OAuth — це task-78. Ця таска — **облікові дані**, на які task-78 спирається; разом із невеликою фазою A (транспорт) вона вже дає віддалений Claude Code / Claude Desktop **без docker**, бо обидва вміють передавати заголовок.

## 1. Скоуп

- Нова сторінка **`#/account`** («Your account») — доступна **всім** ролям, включно з `viewer`. Це перша особиста сторінка в тулі: досі в меню користувача були лише адмінські пункти.
- Секція **Personal access tokens**: список своїх токенів, створення, відкликання.
- Створення токена показує значення **рівно один раз** — тим самим патерном, що task-71 показує згенерований пароль (`showSecret` у `frontend/js/admin-users-page.js`).
- `resolve_agent_token` (task-73) розширюється другим шляхом: пошук по `token_sha256` у БД, який **працює в проді**.
- Журнал task-72 отримує реальну особу за токеном: не «agent», а «Ivan (token: claude-code)».

### 1.1 Не в скоупі — свідомо

- **OAuth і `/mcp`** — task-78. Тут лише облікові дані.
- **Адмінське керування чужими токенами.** Адмін бачить у журналі, що робив чужий токен, і може деактивувати самого користувача (що вбиває всі його токени, §3.2), але не гортає чужі токени поштучно. Причина: перегляд чужих особистих ключів не дає нічого, чого не дає журнал, а спокуса «подивитись» створює зайву поверхню.
- **Service-акаунти без людини.** Токен завжди чийсь. Спільний токен «для CI» — це рівно та проблема, з якої почалась ця таска.

## 2. Модель даних

`agent_tokens` (назва з task-74 §4.2, щоб не плодити синонімів):

| Колонка | Навіщо |
|---|---|
| `id` | PK |
| `user_id` → `users.id` | **власник**; без нього токен не має ні особи, ні ролі |
| `label` | людська назва («claude-code», «ноутбук», «CI») — щоб було що відкликати усвідомлено |
| `token_sha256` | єдине, що зберігається; сам токен — ні |
| `prefix` | перші 8 символів після `yvth_`, **не секрет** — щоб UI показав «yvth_a1b2c3d4…» і людина впізнала свій ключ у списку |
| `role` | роль **цього токена**, ≤ роль власника (§3.3) |
| `created_at`, `expires_at` | термін життя обов'язковий (§3.4) |
| `last_used_at` | «цим ще користуються?» — записується з троттлом (§3.5) |
| `revoked_at` | відкликання, **не** `DELETE` — інакше журнал втратить автора (принцип task-71) |

Хешування — наявний `hash_token()` з `app/db/repositories/users.py`, який уже несе правильне обґрунтування: **sha256, а не scrypt**, бо це 256 випадкових біт, а не пароль людини.

Формат значення: **`yvth_<43 символи base64url>`**. Префікс тут не косметика — він робить токен упізнаваним у чужих логах і придатним до автоматичного пошуку витоків (`grep -r "yvth_"` по репозиторіях і дампах).

## 3. Інваріанти безпеки

Це головна частина таски. Кожен пункт — окремий тест (§6).

### 3.1 Роль резолвиться **наживо**, а не консервується

Токен зберігає `role`, але **фактичні** права на кожен запит = `min(роль токена, поточна роль користувача)`. Якщо адмін завтра понизить людину до `viewer`, її вчорашній admin-токен **сьогодні ж** стає viewer-токеном.

Без цього токен перетворюється на чорний хід, що переживає пониження — рівно те, чого рольова модель task-71 не має допускати.

### 3.2 Деактивація вбиває все

`users.is_active = false` → усі токени цієї людини перестають працювати негайно. Той самий шлях, що вже є для сесій (`resolve_session_sync` перевіряє `user.is_active` на кожен запит) — не окрема логіка, а той самий крок.

### 3.3 Не можна видати собі більше, ніж маєш

Сервер **обрізає** запитану роль до ролі власника. `viewer` не створить `member`-токен, як би не виглядав запит.

Зворотне — **дозволено й заохочується**: `admin` може створити собі `viewer`-токен для скриптів, які лише читають. Це дешевий спосіб дати людині принцип найменших привілеїв у руки, і саме він робить токени безпечнішими за cookie-сесію, а не небезпечнішими.

### 3.4 Термін життя обов'язковий

30 / 90 / 365 днів, дефолт — 90. Варіанта «безстроково» немає: забутий вічний токен у чужому конфізі — найтихіший спосіб втратити доступ назавжди. Протухлий токен дає `401` з явною причиною (не «невірний токен» — людина має розуміти, що саме сталось).

### 3.5 Гарячий шлях лишається холодним

`resolve_agent_token` виконується на **кожен** запит із bearer'ом. Дзеркалимо `resolve_session_sync` буквально: один індексований `SELECT` по `token_sha256`, один `get` по `users`, запис `last_used_at` **не частіше** ніж раз на інтервал, і провал цього запису **ніколи** не валить запит (`try/except` + `rollback` + `warning`, як у сесіях). Урок task-66/67 тут діє незалежно від того, що ми вже на Postgres.

### 3.6 CSRF не застосовується — і це не послаблення

Bearer браузер сам не додає, тож підробити крос-сайтовий запит із ним структурно неможливо (те саме обґрунтування, що в task-73). Але рольова перевірка й журнал — ті самі, що для людини.

### 3.7 Секрет ніде, крім одного HTTP-відгуку

Повне значення існує рівно в тілі відповіді `POST /api/v1/me/tokens`. Далі — тільки `prefix`. Ні в журналі, ні в логах, ні в наступних відповідях API його немає; `RedactionFilter` доповнюється патерном `yvth_…`.

## 4. Журнал (task-72)

Виклик із токеном пише в `audit_events`: `actor_kind="agent"`, але `actor_id`/`actor_email`/`actor_role` — **справжньої людини**, плюс `details.token_label`. У стрічці це читається як «Ivan — via token “claude-code”».

Це і є головна перевага над спільним секретом і над `static_headers` з task-78 §2: журнал не сліпне, коли робота йде через агента.

Створення й відкликання токена — самі по собі мутації, тож теж лишають рядок (`token.create` / `token.revoke`), з `label`, **без значення**.

## 5. API і UI

### 5.1 Ендпоінти (усі — «про себе», без адмінських прав)

| Метод | Шлях | Що |
|---|---|---|
| `GET` | `/api/v1/me/tokens` | свої токени: `label`, `prefix`, `role`, `created_at`, `expires_at`, `last_used_at`, `revoked_at` |
| `POST` | `/api/v1/me/tokens` | створити; **єдина** відповідь із повним значенням |
| `DELETE` | `/api/v1/me/tokens/{id}` | відкликати свій; чужий → `404` (не `403` — щоб не підтверджувати існування чужого id) |

Скоуп «свої» перевіряється на сервері за `Actor`, не за параметром із запиту.

### 5.2 Сторінка `#/account`

- Хто ви: ім'я, email, роль (роль — не редагується, це відповідь на «а що мені взагалі можна»).
- **Personal access tokens**: таблиця (label, prefix, роль, створено, діє до, востаннє використано) + «New token» (label, роль ≤ своєї, термін) + «Revoke» з підтвердженням.
- Після створення — панель одноразового показу з кнопкою Copy і чесним текстом: «показано один раз, відновити не можна, лише перевидати».
- Порожній стан пояснює, **навіщо** це, і веде на `#/mcp/connect`.

### 5.3 Зв'язок із task-77

На `#/mcp/connect` у конфізі зараз стоїть плейсхолдер `<your-token>` і рядок «ask an admin for a token». Після цієї таски там з'являється кнопка **«Create a token»** → `#/account`, а текст міняється на «створіть свій». Це закриває follow-up, записаний у task-77 §10.

## 6. Тести

`tests/unit/auth/` + `tests/unit/api/`:

- **Роль наживо:** admin-токен → користувача понижено до `viewer` → наступний запит уже `viewer`; write → `403`.
- **Деактивація:** `is_active=false` → усі його токени → `401` негайно.
- **Стеля ролі:** `viewer` просить `admin`-токен → отримує `viewer`; `admin` просить `viewer` → отримує `viewer` (пониження дозволене).
- **Термін:** протухлий токен → `401`; причина відрізняється від «невірний токен».
- **Відкликання:** `revoked_at` → `401` з наступного ж запиту; чужий id на `DELETE` → `404`.
- **Одноразовість:** повне значення є рівно в одній відповіді; `GET` ніколи не віддає нічого, крім `prefix`.
- **Секрети:** значення не потрапляє ні в `audit_events`, ні в логи (прямий тест, не сподівання).
- **Ізоляція:** користувач A не бачить і не відкликає токени користувача B.
- **Журнал:** запит із токеном лишає рядок із **реальним** `actor_id`, а не з «agent».
- **Гарячий шлях:** `last_used_at` пишеться не частіше за інтервал; збій запису не валить запит (мок, що кидає `SQLAlchemyError`).
- **Прод:** дев-токен task-73 лишається мертвим на `ENVIRONMENT=production`, особистий — працює. Два різні шляхи, два тести.
- **Закритість:** guard task-71 зелений і непорожній; `/api/v1/me/*` вимагає автентифікації (сесією **або** токеном).

E2E (`tests/e2e/frontend/account-tokens.cjs`): створити → значення показано один раз → перезавантаження показує лише prefix → відкликати → зник зі списку активних.

## 8. Definition of Done

1. Будь-який користувач (включно з `viewer`) створює собі токен у `#/account` і робить ним запит до API — у проді, не лише в dev.
2. Значення показано один раз; у списку далі лише `prefix`.
3. Усі інваріанти §3 покриті тестами й зелені.
4. Журнал показує реальну людину за токеном, з міткою токена.
5. Понижена роль і деактивація вбивають токен **негайно** — перевірено вживу, не лише юнітом.
6. `ruff`, `mypy app`, `pytest tests/unit/auth tests/unit/api` — зелені в Docker.
7. Міграція застосована **після** бекапу за процедурою task-75 §8 (`pg_dump -Fc`).
8. `#/mcp/connect` більше не каже «ask an admin».
9. Жодної нової залежності.
