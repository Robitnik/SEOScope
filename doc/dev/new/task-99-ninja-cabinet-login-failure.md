## §0. Що є сьогодні (виміряно живцем 2026-09-17)

### §0.1 Кабінет відхиляє наші облікові дані

Холодний вхід свіжим контекстом у контейнері, з тими самими `REPORTING_NINJA_EMAIL` /
`REPORTING_NINJA_PASSWORD`, які бачить worker. Після сабміту форми сторінка показує
Vaadin-нотифікацію:

> **We are sorry but there is no user with that email address and password**

`email = yuriih@theyovth.com`, пароль — 8 символів, без лапок і без пробілів по краях
(перевірено окремо: `p == p.strip()`, перший/останній символ не лапка). Тобто це не
проблема екранування в `.env`, а відмова сервера.

Формулювання Reporting Ninja не розрізняє «пароль змінився» і «такого користувача більше
немає» — обидві гіпотези §2 має перевірити, не вгадуючи.

### §0.2 Селектор `.valo-menu-item` не дрейфував

Розмітка кабінету на місці — після сабміту в DOM є `v-app dashboard applicationui`,
`rnPublicForm`, `v-button primary`, `v-Notification failure`. `.valo-menu-item` дає 0 вузлів
не тому, що перейменувався, а тому, що **меню й не мало з'явитися**: входу не сталося.
Правити селектор не треба — це була б правка симптому.

### §0.3 Впав ЛИШЕ PDF-шлях

REST-ключ Reporting Ninja живий, перевірено проти справжнього ендпоінта:

| Ключ | `POST https://api.reportingninja.com/v1/fields` |
|---|---|
| Наш `REPORTING_NINJA_API_KEY` | `200 ok` |
| Свідомо сміттєвий | `401 AUTH_INVALID` |

Тобто джерела `api` і `google_api` не зачеплені взагалі. Оператор, якому потрібні цифри
**зараз**, має два робочі шляхи — це і є межа терміновості інциденту.

### §0.4 Вікно поломки

| Подія | Коли |
|---|---|
| Останній успішний PDF-прогін | 2026-09-08 06:35 |
| Перший збій | 2026-09-17 13:35 |

Дев'ять днів між ними, жодного PDF-прогону всередині. Момент зміни пароля з логів звітів
не відновлюється.

### §0.5 Відмова облікових даних приходить як `internal_error` із сирим таймаутом

[`_login`](../../../app/reports/ninja_browser.py#L219-L228) після кліку чекає рівно одну річ —
успіх:

```python
page.locator("div.v-button.primary").click()
page.wait_for_selector(".valo-menu-item", timeout=30_000)
```

Нотифікація про відмову з'являється приблизно за секунду, але її ніхто не читає. Playwright
кидає `TimeoutError` через 30 с, `AuthenticationFailedError` **не виникає**, і
[runner.py#L321](../../../app/reports/runner.py#L321) записує `internal_error` з текстом
`Page.wait_for_selector: Timeout 30000ms exceeded…`. Саме це й показано оператору.

Підтверджено в бойовій БД:

```
failed | internal_error | Page.wait_for_selector: Timeout 30000ms exceeded. … locator(".valo…
```

Класифікація помилки бреше: `auth_failed` — точний код, і він уже існує в кодовій базі.

### §0.6 На цьому шляху не знімається скріншот

Модуль обіцяє в докстрінгу «a screenshot artifact on every failed attempt, not just the final
one», але `_capture_failure_screenshot` викликається лише в циклі періодів
([#L550-L553](../../../app/reports/ninja_browser.py#L550-L553)).
[`_ensure_session`](../../../app/reports/ninja_browser.py#L519-L523) виконується **до** цього
циклу й поза `try`. Тому збій входу не лишає жодного доказу: ні знімка, ні тексту нотифікації.
Мені довелося написати одноразовий probe-скрипт, щоб побачити те, що застосунок міг зберегти сам.

Показово: у прогоні `0 of 6 periods` і «This run failed before any period was collected» —
тобто система точно знала, що впала саме на етапі сесії, і все одно нічого про нього не сказала.

### §0.7 UI пропонує ретрай, який не може спрацювати

Сторінка прогону показує **Retry (use cached PDFs)** і **Rebuild (re-download)** для будь-якого
`failed`. Для відмови облікових даних обидві кнопки — по 30 с очікування й той самий текст.
Це рівно той дефект, який task-49 §2.3 уже закрив для `report_name_missing`, але **тільки в
матриці батчів** ([reports-batch.js#L152](../../../frontend/js/reports-batch.js#L152)); сторінка
одиночного прогону такої логіки не має взагалі, і `auth_failed` не згадується у фронті звітів
ніде.

### §0.8 Де живуть облікові дані (змінено 2026-09-17)

Раніше — не в цьому репо: `compose.yaml` підтягував їх через
`env_file: ${AISEOTOOLS_PATH}/.env`. **Тепер усі секрети провайдерів перенесені у `.env` цього
репо** (gitignored, не відстежується), і `env_file` вказує на нього. Значення перенесено
байт-у-байт: `docker compose config` до і після показує нуль змінених і нуль зниклих змінних.

Важливо для §2: пароль у трьох місцях (старий `AISeoTools/.env`, новий `.env`, живий контейнер)
**збігався байт-у-байт** — гіпотезу «контейнер просто не перечитав файл» перевірено й відкинуто.
Пароль недійсний сам по собі, а не застарілий у якійсь одній копії.

Побічний ефект переїзду, вартий згадки: два файли, які обидва мусили бути правильними, — це
окремий клас відмови поверх цього інциденту. Тепер файл один.

## §2. Крок 0 — розблокування (поза кодом, потребує людини)

Жодна зміна коду не поверне PDF, доки кабінет відхиляє пароль. Порядок:

1. Зайти на `https://app.reportingninja.com` вручну як `yuriih@theyovth.com`.
   - Якщо вхід проходить — пароль у `AISeoTools/.env` просто застарів, переходь до п.2.
   - Якщо не проходить — з'ясувати, чи акаунт ще існує і чи не знято з нього місце
     (формулювання Reporting Ninja не розрізняє ці випадки, §0.1). Тоді це питання до
     власника підписки, а не до `.env`.
2. Оновити `REPORTING_NINJA_PASSWORD` у `.env` цього репо (§0.8 — секрети переїхали сюди).
3. Прибрати протухлий стан сесії, щоб наступний прогін пішов чистим логіном:
   ```bash
   docker compose exec api rm -f /app/app_data/.ninja_session.json
   ```
4. Підняти стек заново — `env_file` читається на старті контейнера, не на кожен прогін:
   ```bash
   docker compose up -d
   ```
5. Перевірити за 10 секунд, а не годинним батчем (команда з §3.6):
   ```bash
   docker compose exec api poetry run yovth-report ninja-cabinet-check
   ```

**Запобіжник:** не ганяти повторні спроби входу наосліп. Після кількох невдач акаунт можна
заблокувати, і тоді проблема з «застарілий пароль» перетвориться на «заблокований акаунт».
Бюджет у `relogin_budget = [1]` уже обмежує один прогін; ручні спроби теж варто рахувати.

## §3. Зміни в коді

### §3.1 `_login` читає РЕЗУЛЬТАТ, а не лише успіх

Після кліку чекати перший із двох результатів — меню (успіх) або нотифікацію про помилку —
і не витрачати 30 с на те, що вирішується за секунду:

```python
page.locator("div.v-button.primary").click()
outcome = _await_login_outcome(page, timeout_ms=30_000)
if outcome.rejected:
    raise AuthenticationFailedError(
        f"Reporting Ninja rejected the cabinet sign-in: {outcome.message}"
    )
```

`_await_login_outcome` опитує в циклі (~250 мс) дві умови:

| Умова | Селектор | Висновок |
|---|---|---|
| Успіх | `.valo-menu-item` видимий | увійшли |
| Відмова | `.v-Notification.failure` видима | `rejected`, текст беремо звідти |

Текст нотифікації віддаємо як є — він описує акаунт, а не секрет, і не містить ні пароля, ні
ключа (перевірено на живому зразку, §0.1). Обрізати до ~200 символів, щоб чужий HTML не
розповзався по журналу подій.

**Чому цикл, а не `Promise.race`:** синхронний Playwright-API не має гонки очікувань, а два
послідовних `wait_for_selector` з коротким таймаутом дали б фальшиву відмову на повільному
входi. Цикл дає симетричне очікування обох наслідків.

### §3.2 Скріншот на збої входу

`_ensure_session` і `_login` отримують необов'язковий `screenshots_dir` і кладуть туди
`login_failed.png` перед тим, як кинути `AuthenticationFailedError`. Це закриває розрив між
докстрінгом модуля і його поведінкою (§0.6) — саме той артефакт, якого мені бракувало.

### §3.3 Коректний тип помилки навіть на таймаут

Якщо не з'явилось ані меню, ані нотифікації, це все одно збій **сесії**, а не невідомий
внутрішній збій. Кидати `AuthenticationFailedError` із чесним текстом
(«sign-in neither completed nor was rejected within Ns»), щоб `internal_error` лишався за
справжніми несподіванками.

### §3.4 Преflight-подія про вхід

Перед першим періодом емітити `("info", "preflight", "Reporting Ninja cabinet: signed in", {})`.
Сьогодні в журналі прогону немає жодного сліду етапу входу — саме тому збій виглядав як збій
«нізвідки». Пошту в подію не класти: вона не потрібна для діагностики й це зайвий PII у журналі.

### §3.5 UI: `auth_failed` не пропонує ретрай

У [reports-run.js](../../../frontend/js/reports-run.js) для `error_code === "auth_failed"`:

- прибрати **Retry** і **Rebuild** — жодна з них не може допомогти (§0.7);
- показати конкретну наступну дію: `Reporting Ninja rejected the cabinet sign-in. Update the
  cabinet password, then run this report again.` (UI-копірайт англійською, AGENTS §14);
- лишити текст помилки від провайдера видимим.

Дзеркало того, що task-49 §2.3 зробив для `report_name_missing` у матриці батчів. Заразом варто
перевірити, чи матриця батчів не пропонує `Retry` для `auth_failed` — там та сама логіка
підбору дій.

### §3.6 `yovth-report ninja-cabinet-check`

Окрема команда: бере `cabinet_lock`, робить один холодний вхід, друкує `ok` / текст відмови,
кладе знімок екрана і виходить із кодом 0/1. Причина проста — сьогодні єдиний спосіб дізнатися,
чи живі облікові дані кабінету, це запустити звіт на 6 періодів і чекати. Ця команда робить те
саме за ~10 с і стає п'ятим кроком §2.

## §6. Ризики

- **Акаунт може бути не просто з новим паролем, а видалений/без місця.** §2 п.1 розрізняє це
  вручну, бо Reporting Ninja у відповіді не розрізняє. Якщо так — обсяг змінюється з «оновити
  секрет» на «відновити доступ до підписки», і код із §3 усе одно лишається потрібним.
- **Повторні невдалі входи можуть заблокувати акаунт.** Тому §3.1 навмисно робить відмову
  ШВИДКОЮ і термінальною — жодних автоматичних повторів на `rejected`, `relogin_budget`
  лишається одиницею.
- **Текст нотифікації — чужий HTML.** Обрізати й екранувати; він іде в подію, а звідти у фронт.
